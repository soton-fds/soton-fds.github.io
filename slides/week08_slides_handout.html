What is Shiny?

Sharing an analysis

So far, our results reach other people as static reports: they see the plots and tables we chose.

Shiny is an R package for building interactive web apps entirely in R:

  • users change the inputs (e.g. choose a subset, move a slider) and the results update in their browser
  • you write only R; Shiny generates the website (HTML, CSS and JavaScript)

The audience: people who don’t program in R.

Open the gallery examples now, briefly (1–2 min total):

  • Movie Explorer — filters and selectors over a films dataset.
  • Radiant — an entire statistics package built as a Shiny app.

The point: everything they have done so far in the course could sit behind an app like this.

Setting up

install.packages("shiny")   # once, in the console
library(shiny)              # at the top of every app script
  • shiny is not part of the tidyverse
  • apps are written in .R scripts, not .qmd files — a rendered Quarto document is a static web page, with no R running behind it
  • convention: one script, app.R, ending in shinyApp(ui, server)

Anatomy of a Shiny App

Hello Shiny

library(shiny)

ui <- fluidPage(
  titlePanel("Hello Shiny!"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("num", "Choose a number:", 1, 100, 50)
    ),
    mainPanel(
      textOutput("result")
    )
  )
)

server <- function(input, output, session) {
  output$result <- renderText({
    paste("You selected:", input$num)
  })
}

shinyApp(ui, server)

Walk through the code top to bottom:

  • ui: what the page looks like. fluidPage is the root; it becomes an HTML page styled with Bootstrap. Resize the window to show it adapting.
  • server: a function that connects inputs to outputs. session is advanced — we won’t use it.
  • shinyApp(ui, server) ties them together and starts a web server.

The naming contract

ImportantTask

How does the server know which slider to read, and where to put the text?

By name:

In the UI In the server
sliderInput("num", ...) read it as input$num
textOutput("result") fill it with output$result <- renderText(...)

Every input’s first argument is its name; every output’s name must match an output$... assignment.

This is the backbone of every app. A mismatched output name gives no error — the output just stays blank. That’s the most common silent bug; we’ll come back to it.

Add an output

ImportantTask

Extend the app so that it also shows the square of the chosen number.

# in the UI, inside mainPanel(), after a comma:
textOutput("result"),
textOutput("squared")

# in the server:
output$squared <- renderText({
  paste("Its square is:", input$num^2)
})

Two changes, joined by a name: a slot in the UI, and a render* function in the server.

Do this live in app1_hello.R. Deliberately forget the comma after textOutput("result") first and run it: the error is unexpected symbol, pointing at the component after the gap. The UI is one big nested function call, so every component needs a comma. (A trailing comma after the last one is harmless.)

Running an app

Three ways to start it:

  1. define ui and server, then run shinyApp(ui, server)
  2. save as app.R and call runApp() (or runApp("path/to/app"))
  3. click Run App in RStudio
Listening on http://127.0.0.1:3689

Shiny starts a web server on your computer. The browser and the R process stay connected: each change to an input is sent to R, which sends back updated outputs.

While the app runs your console is busy — stop it (stop icon, or Esc) to get your prompt back.

Reactivity

Does the server re-run?

ImportantTask

When the user moves the slider, which code runs again?

Not the whole server function — only the renderText({...}) block, because it reads input$num, which has changed.

Shiny keeps a reactive graph: a record of which code reads which values. When a value changes, it re-runs only what depends on it.

Sources, conductors and endpoints

Every piece of reactive code plays one of three roles in the graph:

  • Sources hold values that change over time: the inputs the user sets, or values the server creates itself
  • Conductors sit in the middle: they read sources, compute something from them, and pass the result on
  • Endpoints sit at the end, where reactive code has an effect: outputs update what the user sees; observers do something else

The Hello app is the smallest possible graph: one source (input$num) straight into one endpoint (output$result). It has no conductor; the next app has one.

Three roles in the graph

Role Created with Read with
Source *Input("x", ...) in the UI input$x
Source x <- reactiveVal(initial) x(); set with x(new_value)
Conductor x <- reactive({...}) x()
Endpoint (output) output$x <- render*({...}) displayed by *Output("x")
Endpoint (observer) observe({...}), observeEvent(e, {...}) not read: run for side effects

Point out that conductors and reactiveVals are read by calling them, x(), like a function. reactiveValues() is a third kind of source, a list-like version of reactiveVal; it’s in the notes.

A sampling app

We want an app that draws a random sample of 500 points, whose \(x\) and \(y\) coordinates are normally distributed with means \(\mu_1\) and \(\mu_2\) chosen by the user.

It should show the sample in a scatter plot, and print the sample means beneath it. Separately, it greets the user by name.

Two outputs need the same sample. Where should it be drawn?

Leave the question hanging: the next slide shows one answer, and the slides after it explain why.

A conductor

server <- function(input, output, session) {
  samples <- reactive(tibble(
    x1 = rnorm(500, input$mu1, 1),
    x2 = rnorm(500, input$mu2, 1)
  ))

  output$plot <- renderPlot({
    ggplot(samples(), aes(x = x1, y = x2)) +
      geom_point() +
      coord_cartesian(xlim = c(-5, 5), ylim = c(-5, 5))
  })

  output$means <- renderText({
    paste("Sample means:", round(mean(samples()$x1), 2), "and",
          round(mean(samples()$x2), 2))
  })

  output$greeting <- renderText(paste("Hello", input$name))
}

The new piece is samples <- reactive(...): a conductor. It draws the sample, and both the plot and the means read it by calling samples(). The greeting doesn’t touch it. Say explicitly that we’ll see over the next few slides why the sample is drawn in a reactive() rather than inside each render* block.

The UI (in app2_samples.R) has two numericInputs (mu1, mu2) and a textInput (name), laid out with fluidRow/column.

coord_cartesian fixes the axes, so the cloud visibly moves rather than the axes rescaling around it.

A conductor: running

DEMO: run app2_samples.R. Change mu1: the cloud moves and the means update. Then type in the name box: only the greeting changes, the points stay exactly where they are. Leave the question of why to the next slide.

The reactive graph

Sources → conductor → endpoints. An arrow means “is read by”.

Changing \(\mu_1\) re-runs samples(), the plot and the means. Typing a name re-runs only the greeting.

Walk through the graph once, left to right: three sources, one conductor, three endpoints. Then trace a change to mu1 along the arrows, and then a change to the name.

Point out that samples() is computed once per change even though two endpoints call it: the first caller recomputes it, the second gets the cached result. That caching is the subject of the next slide.

Why not skip the conductor?

ImportantTask

Why not just call rnorm() inside each render* block?

Each output would draw its own sample: the means printed under the plot would describe different points from the ones plotted.

A reactive() computes the sample once and caches it, so every output sees the same data — and it is only recomputed when input$mu1 or input$mu2 changes.

If asked: putting set.seed() at the top of the reactive makes each redraw use the same random numbers, so changing mu1 just slides the cloud (links back to week 3’s reproducibility).

Spot the bugs

ImportantTask

Each line below is inside server. Each fails. Why?

mean_x1 <- mean(samples()$x1)                      # (a)
output$means <- renderText(mean(samples$x1))       # (b)
input$mu1 <- 0                                     # (c)

  1. reactive values can only be read inside reactive code (reactive, render*, observe*): “Operation not allowed without an active reactive context”.

  2. missing parentheses: samples is a function, so samples$x1 gives “object of type ‘closure’ is not subsettable”. Use samples()$x1.

  3. inputs are read-only — the user sets them. If the server needs a value it can change, use reactiveVal().

Observers: making things happen

Rule of thumb:

  • compute a value for other code to use → reactive()
  • make something happen → an observer

Two kinds of observer

  • observe({...}) re-runs when anything it reads changes
  • observeEvent(event, {...}) re-runs only when event changes
observe({
  message("mu1 is now ", input$mu1)   # prints to the R console
})

A cheap way to watch the graph at work — and a useful debugging trick.

A counter

ImportantTask

An app has two buttons and a line of text:

ui <- fluidPage(
  actionButton("inc", "Increase counter"),
  actionButton("reset", "Reset counter"),
  textOutput("value")
)

Write the server so that the text shows a count that the buttons increase and reset. There’s no input holding the count — where does it live?

server <- function(input, output, session) {
  counter <- reactiveVal(0)           # a source the server can change

  observeEvent(input$inc, {
    counter(counter() + 1)            # set by calling with a value
  })

  observeEvent(input$reset, {
    counter(0)
  })

  output$value <- renderText({
    paste("Counter is:", counter())   # read by calling it
  })
}

DEMO: run app3_counter.R and click both buttons.

  • An actionButton’s value is just the number of presses — rarely worth showing. What matters is that a press happened: an event, so pair it with observeEvent. By default observeEvent ignores the starting value 0, so nothing runs on start-up.
  • The observers change the reactiveVal; the renderText reads it, so it re-runs automatically.
  • Don’t use an observer to compute a value and stash it in a reactiveVal for others to read — that’s what reactive() is for.

Three new ideas

Read the data once, outside the server, not on every change:

penguins <- read_csv("data/penguins.csv")

A range slider: give value two numbers, and read both ends in the server:

sliderInput("mass", "Body mass (g):", min = 2700, max = 6300,
            value = c(2700, 6300))
filter(body_mass_g >= input$mass[1], body_mass_g <= input$mass[2])

Wait for the user: req() draws nothing until a species is chosen:

output$plot <- renderPlot({
  req(input$species)
  ...
})
  • Data read inside the server would be re-read from disk every time an input changes.
  • The species dropdown starts on a named empty choice, "(Choose a species)" = "". input$species is then "", which req() treats as “not chosen yet”, so the output stays blank. validate() and need() give a friendlier message; they’re in the notes.

Sharing and limitations

Deploying

Locally, the app runs in your R session — anyone else needs R and every package.

Deploying puts the app on a server (e.g. shinyapps.io, or your own Shiny Server) and gives users a web link. They need only a browser.

Common uses: dashboards, data exploration tools, statistical “what-if” calculators, teaching demos, prototypes for stakeholders.

Limitations

ImportantTask

You deploy the penguin explorer and 200 people use it at once. Then you add a text box that lets users type a filter condition, run with eval(parse(text = input$filter)). What could go wrong?

  • Performance / scalability: one R process serves everyone, and R does one thing at a time — a slow computation for one user makes everyone wait
  • Security: never run user input as code (or paste it into a SQL query — SQL injection, week 7). Anyone with the link can see the data: think twice before showing personal data (ethics week)
  • Cost and hosting: free tiers are limited; beyond them, hosting costs money or expertise
  • Customisation: polished interfaces may need HTML/CSS/JavaScript
