SQL for Data Science

Objectives

By the end of this lecture you will be able to:

  • explain what a relational database adds to a folder of CSV files
  • read SQL queries — including joins, GROUP BY and subqueries — and say what they return
  • decide whether work should be done in the database or in R, and use dbplyr to query a database with dplyr code

Set expectations early: students will not be asked to write SQL. They must be able to read it, and to work with databases from R via dbplyr. Today’s SQL is all run against a small database built from the student tables of week 5.

What you need to know

ImportantFor the assessment

You will not be asked to write SQL. You should be able to read a SQL query — including joins, GROUP BY and subqueries — and say what it does and what it returns. To work with a database yourself, you’ll write dplyr code and let dbplyr translate it into SQL.

Say this plainly: every SQL task today is “what does this return?”, never “write this query”. The skill is reading.

Why databases?

CSV files

Until now, all our data has come from CSV files:

  • a flat table of text
  • no types — R has to guess them
  • no validation of what goes in
  • no way to say how one file relates to another

Remember week 5?

ImportantTask

student_grades.csv contains grades for students 21 and 22, who don’t appear in student_data.csv. Should that be possible? Could a CSV file stop it?

It shouldn’t be possible: a grade must belong to a student. But a CSV file is just text — nothing checks it. We only found the problem by joining.

A relational database can refuse to store it in the first place.

Relational databases

A database holds tables (like data frames), plus rules about them:

  • every column has a type, checked on the way in
  • a primary key uniquely identifies each row
  • a foreign key must match a primary key in another table (each grade’s student_id must be a real student)

We query it in SQL: you say what you want; the database works out how.

SQL is Structured Query Language. It is declarative: a query describes the result, not the steps to compute it. A student’s id is the primary key of the students table.

Why use one?

  • Integrity: types and keys keep data consistent
  • Scale: data lives on disk, not in memory; the server may be far more powerful than your laptop
  • Security: access controls and permissions
  • Concurrent access: many users reading and writing safely
  • Less duplication: related tables instead of one big one (week 5)

PostgreSQL, MySQL, SQL Server, Oracle… we use SQLite: a single file, no server. Each system has its own dialect of SQL.

Non-relational (“NoSQL”) databases such as MongoDB exist too, but are out of scope.

Reading SQL

Creating tables

CREATE TABLE students (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    given_name TEXT,
    family_name TEXT,
    date_of_birth INTEGER
);
CREATE TABLE grades (
    student_id INTEGER,
    course TEXT,
    grade REAL,
    FOREIGN KEY (student_id) REFERENCES students(id)
);

Types are declared up front. AUTOINCREMENT generates new IDs; the FOREIGN KEY ties each grade to a student. Keywords are in CAPITALS by convention; comments start with --.

Behind the scenes, the 20 students and their grades from week 5 have been inserted — except the grades for the non-existent students 21 and 22. SQLite only checks foreign keys if you switch it on (PRAGMA foreign_keys = ON), which we have done; database servers check them by default.

Inserting a bad row

ImportantTask

What happens if we try to store a grade for student 21?

INSERT INTO grades(student_id, course, grade) VALUES (21, 'MATH6195', 70);
Error: FOREIGN KEY constraint failed

The database refuses it. The problem from week 5 can’t happen.

INSERT is the C of CRUD: Create, Read (SELECT), Update (UPDATE) and Delete (DELETE). We’ll only read from here on; the notes show UPDATE and DELETE. Both change the database permanently, and without a WHERE they affect every row.

JOIN

ImportantTask

What does this return? Which students are missing from it?

SELECT students.given_name, students.family_name,
       grades.course, grades.grade
FROM grades
    JOIN students ON grades.student_id = students.id;
Displaying records 1 - 4
given_name family_name course grade
Adaora Nkomo MATH6195 68
Hiroshi Tanaka MATH6195 67
Aaliyah Williams MATH6195 68
Dimitri Volkov MATH6195 74

One row per grade, with the student’s name attached. JOIN is an inner join, so student 7 (no grades) is missing — exactly inner_join() from week 5. LEFT JOIN and FULL OUTER JOIN also exist.

table.column says which table each column comes from.

GROUP BY

ImportantTask

What does this return?

SELECT course, COUNT(*) AS n, AVG(grade) AS mean_grade
FROM grades
GROUP BY course;
3 records
course n mean_grade
MATH2010 17 64.47059
MATH2011 18 70.27778
MATH6195 18 67.94444

One row per course, with its number of grades and mean grade — group_by() then summarise(). AS names a calculated column.

Every column in the SELECT must either be in the GROUP BY or be an aggregate like COUNT, SUM, AVG. COUNT(*) counts rows; COUNT(column) counts non-missing values.

Subqueries

ImportantTask

What does this return? Read the inner query first.

SELECT given_name, family_name
FROM students
WHERE id IN (
    SELECT student_id
    FROM grades
    GROUP BY student_id
    HAVING AVG(grade) > 75
);
2 records
given_name family_name
Tariq Ibn Rashid
Amina Okonkwo

The inner query finds the IDs of students whose average grade is over 75; the outer query looks up their names. HAVING filters groups; IN compares against a list.

NOT IN works too: WHERE id NOT IN (SELECT student_id FROM grades) finds student 7 — the anti_join() of week 5.

Missing values

Missing values in SQL are NULL, like NA in R.

  • test for them with IS NULL / IS NOT NULL: a comparison such as grade = NULL is never true
  • aggregates such as AVG and SUM skip NULLs, as if na.rm = TRUE

NULL means unknown, so comparing anything with it gives “unknown”, which a WHERE treats as false.

How to read a query

Written in a fixed order, starting with SELECT — but run in this order:

  1. FROM, JOIN
  2. WHERE
  3. GROUP BY
  4. HAVING
  1. SELECT
  2. DISTINCT
  3. ORDER BY
  4. LIMIT

So start reading at FROM.

This explains the rules: WHERE runs before grouping, so it can’t use COUNT(*) — that’s what HAVING is for.

SQL to dplyr

ImportantTask

Rewrite this query as a dplyr pipeline on a tibble grades.

SELECT student_id, COUNT(*) AS n_courses
FROM grades
WHERE grade >= 60
GROUP BY student_id
HAVING COUNT(*) > 1
ORDER BY n_courses DESC
LIMIT 5;
grades |>
  filter(grade >= 60) |>               # WHERE
  group_by(student_id) |>              # GROUP BY
  summarise(n_courses = n()) |>        # SELECT ... COUNT(*) AS
  filter(n_courses > 1) |>             # HAVING
  arrange(desc(n_courses)) |>          # ORDER BY ... DESC
  head(5)                              # LIMIT

The dplyr steps appear in the order SQL runs them.

SQL from R

Where should the work happen?

In the database, importing only the result:

  • less data to transfer — a summary of millions of rows may be a few rows
  • data larger than memory
  • speed: databases are built for this
  • privacy: individual-level data never leaves the database

…or in R?

In R, after importing the tables:

  • R can do far more: models, plots, packages
  • simpler when the data are small

Usually both: the database filters, joins and summarises; R does the rest.

dbplyr

library(dbplyr)

students <- tbl(con, "students")   # con: made with dbConnect()
grades <- tbl(con, "grades")
print(grades, n = 4)

A lazy table: ?? rows, because R hasn’t read the table — it’s still in the database.

Connecting to a database file looks like this:

library(DBI)
con <- dbConnect(RSQLite::SQLite(), "data/customers.db")

DBI, RSQLite and dbplyr are separate installs, not part of the tidyverse. dbGetQuery(con, "SELECT ...") runs raw SQL and returns a data frame.

dplyr in, SQL out

ImportantTask

Use dplyr to find each course’s number of grades and mean grade. Then look at the SQL that dbplyr writes.

query <- grades |>
  group_by(course) |>
  summarise(n = n(), mean_grade = mean(grade, na.rm = TRUE))

show_query(query)
<SQL>
SELECT `course`, COUNT(*) AS `n`, AVG(`grade`) AS `mean_grade`
FROM `grades`
GROUP BY `course`

collect()

class(query)
[1] "tbl_SQLiteConnection" "tbl_dbi"              "tbl_sql"             
[4] "tbl_lazy"             "tbl"                 
query |> collect()
# A tibble: 3 × 3
  course       n mean_grade
  <chr>    <int>      <dbl>
1 MATH2010    17       64.5
2 MATH2011    18       70.3
3 MATH6195    18       67.9

Nothing runs until collect() (or printing). collect() runs the SQL in the database and brings the result into R as a tibble.

sql_render(query) returns the SQL as a string, so it can be passed to dbGetQuery() to check it — in the notes.

Collect as late as possible

ImportantTask

Both give the same answer. Which is better, and why?

grades |> filter(grade > 80) |> collect()
grades |> collect() |> filter(grade > 80)

The first: the filter runs in the database, and only matching rows are sent to R. The second transfers the whole table, then throws most of it away. On millions of rows, that’s seconds versus not fitting in memory.

Limits of the translation

students |>
  mutate(padded = stringr::str_pad(given_name, 10)) |>
  collect()
Error in `stringr::str_pad()`:
! `str_pad()` is not available in this SQL variant.

Only functions dbplyr can translate to SQL work before collect(). Do what you can in the database, collect(), then use the rest of R.

Joining a tibble

prizes <- tibble(id = c(11, 6), prize = c("Gold", "Silver"))
students |> inner_join(prizes, by = "id")
Error in `auto_copy()`:

ℹ `y` is a <tbl_df/tbl/data.frame> object.

A lazy table can only join to tables in the same database.

Copying it in

Either copy = TRUE (copy the tibble into the database), or collect() first:

students |>
  inner_join(prizes, by = "id", copy = TRUE) |>
  select(given_name, family_name, prize) |>
  collect()
# A tibble: 2 × 3
  given_name family_name   prize 
  <chr>      <chr>         <chr> 
1 Tariq      Ibn Rashid    Gold  
2 Rajesh     Krishnamurthy Silver

Joining two lazy tables in the same database works just like dplyr: grades |> inner_join(students, by = c("student_id" = "id")). Finish with dbDisconnect(con) to close the connection.
