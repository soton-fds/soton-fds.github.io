Working with Big Data

Objectives

By the end of this lecture you will be able to:

  • explain what makes data “big”, and why in-memory tools like the tidyverse fail on it
  • identify whether memory, storage or compute is the bottleneck, and the tradeoffs between them
  • describe the main strategies — doing the work in a database, and processing data in chunks (map-reduce) — and the tools that implement them in and outside R

What you need to know

What is big data?

The three Vs

  • Volume: too much to store or load — terabytes, petabytes
  • Velocity: arrives faster than it can be processed — e.g. a live stream of every post on a social media site
  • Variety: many types and sources — tables, text, images, sensor data

“Big” is relative: it depends on your hardware and tools. What’s big for a laptop is routine for a cluster.

Why is it a problem?

Task

Our flight prices file is 29 GB. A typical laptop has 16 GB of memory. What happens if we run read_csv("data/itineraries.csv")?

read_csv loads the whole file into memory as a tibble — and it doesn’t fit. R fails, or the computer slows to a crawl as it swaps memory to disk.

But we don’t need it all in memory to compute, say, a mean: we could read each value once, keep a running total and a count, and throw the value away.

Three resources

Resource Speed Size Limits
Memory very fast 8–32 GB what can be loaded
Storage much slower GBs – TBs how fast data are read
Compute — cores how fast we calculate

The workflow runs as fast as its bottleneck. Big data work is trading them off: reading in chunks uses less memory, but takes longer.

Memory is RAM: what the tidyverse works in. Storage is the disk. Compute is the CPU (or GPU). Storage speeds: a solid-state drive is far slower than memory, a spinning hard drive slower still. Compute: many cores, and GPUs, help when work can be split into independent pieces — at the cost of complexity.

Find the bottleneck

Task

What limits each of these? How would you cope?

  1. Summarising a 1 TB CSV file on a laptop
  2. Analysing a live stream of every post on a social media site
  1. Storage: it can’t be loaded, so it must be read from disk in pieces (or loaded into a database). At ~500 MB/s, one pass through 1 TB takes over half an hour — so compute everything you need in as few passes as possible.
  2. Compute (or the network): data may arrive faster than one machine can process it. Process each record as it arrives keeping running summaries, discard what you don’t need early, and share the work across many machines.

Is my data actually big?

Before reaching for special tools:

library(tidyverse)
penguins <- read_csv("data/penguins.csv")
format(object.size(penguins), units = "KB")
[1] "32.3 Kb"
fares <- read_csv(
  "data/itineraries.csv",
  col_select = c(startingAirport, baseFare),   # only the columns you need
  n_max = 100000                               # develop on a subset
)
format(object.size(fares), units = "MB")
[1] "1.5 Mb"

Check the file size on disk first: it’s a rough guide to the memory needed. n_max reads the first rows, which may not be representative of the rest — fine for writing and testing code, not for final results.

Tools

Better storage

A CSV must be read in full, even to get one column.

  • Relational databases (week 7): data on disk, indexes, powerful servers
  • Columnar formats — Parquet, Feather: each column stored together, so you read only the columns you need
  • HDF5: large arrays and scientific data, with fast access to subsets

Beyond one computer

  • Hadoop: distributed storage (HDFS) and processing (MapReduce) across a cluster
  • Apache Spark: fast cluster computing, with APIs for R, Python, Scala, Java

R on top

R is often a layer on top of these tools, rather than the engine:

  • dbplyr — dplyr code run in a database (week 7)
  • sparklyr — dplyr code run on a Spark cluster
  • duckdb / duckplyr — a fast analytical database, in-process
  • readr::read_csv_chunked() — simple map-reduce in plain R

DuckDB

A database without a server

DuckDB runs inside your R session, and can query a CSV file on disk without loading it.

library(duckplyr)
flights <- read_csv_duckdb("data/itineraries.csv")
flights |> summarise(n = n())
# A duckplyr data frame: 1 variable
         n
     <int>
1 82138753

DEMO (optional): run these live — the count takes ~20 s on 82 million rows. Open Activity Monitor while it runs: memory barely moves, all CPU cores are busy. That’s the point.

Mean fare by airport

Task

Compute the mean baseFare for each startingAirport, the usual way.

flights |>
  group_by(startingAirport) |>
  summarise(mean_base_fare = mean(baseFare, na.rm = TRUE))
Error in `group_by()`:
! This operation cannot be carried out by DuckDB, and the input is a
  stingy duckplyr frame.
• Try `summarise(.by = ...)` or `mutate(.by = ...)` instead of `group_by()` and
  `ungroup()`.
ℹ Use `compute(prudence = "lavish")` to materialize to temporary storage and
  continue with duckplyr.
ℹ See `vignette("prudence")` for other options.

Read the error out: duckplyr can’t run group_by() inside DuckDB, and rather than silently pulling 29 GB into R, it stops. The message tells you the fix. General lesson: these tools support most of dplyr; when something fails, the error message usually says how to rewrite it.

Use .by

flights |>
  summarise(mean_base_fare = mean(baseFare, na.rm = TRUE),
            .by = startingAirport) |>
  arrange(desc(mean_base_fare)) |>
  print(n = 6)
# A duckplyr data frame: 2 variables
  startingAirport mean_base_fare
  <chr>                    <dbl>
1 OAK                       466.
2 SFO                       383.
3 JFK                       329.
4 LAX                       328.
5 IAD                       322.
6 PHL                       295.

The whole query runs in DuckDB, streaming through the file; only the 16 rows of the result come back to R.

Same thing, with dbplyr

library(DBI)
library(dbplyr)
con <- dbConnect(duckdb::duckdb())
flights_db <- duckdb::tbl_file(con, "data/itineraries.csv")

flights_db |>
  group_by(startingAirport) |>
  summarise(mean_base_fare = mean(baseFare, na.rm = TRUE)) |>
  show_query()
<SQL>
SELECT startingAirport, AVG(baseFare) AS mean_base_fare
FROM (FROM 'data/itineraries.csv') q01
GROUP BY startingAirport

Exactly week 7 — a lazy table, translated to SQL — except the FROM names a CSV file. collect() would give the same 16 rows.

Map-reduce

Split, summarise, combine

  • map: process each chunk independently, keeping only a small summary
  • reduce: combine the summaries into the answer

Only one chunk is in memory at a time.

In Hadoop, the chunks are processed on many machines at once: that’s where the speed comes from.

What should each chunk return?

Task

To find the mean body mass of the penguins, we split the data into chunks of 100 rows. Why not just average the four chunk means?

mass <- penguins$body_mass_g
chunks <- split(mass, ceiling(seq_along(mass) / 100))
lengths(chunks)
  1   2   3   4 
100 100 100  44 
mean(map_dbl(chunks, \(x) mean(x, na.rm = TRUE)))   # mean of chunk means
[1] 4139.497
mean(mass, na.rm = TRUE)                            # the true mean
[1] 4201.754

The chunks have different sizes, so their means can’t simply be averaged. Return a sum and a count from each chunk: those can be added up.

General principle: the map step must return enough to combine the partial results exactly. Sums and counts add; means, medians don’t.

Chunks in R

summarise_chunk <- function(chunk, pos) {          # map: one chunk
  chunk |>
    group_by(species) |>
    summarise(sum_mass = sum(body_mass_g, na.rm = TRUE),
              n = sum(!is.na(body_mass_g)), .groups = "drop")
}

results <- read_csv_chunked(
  "data/penguins.csv",
  callback = DataFrameCallback$new(summarise_chunk),
  chunk_size = 100,
  col_types = cols_only(species = col_character(),
                        body_mass_g = col_double())
)

read_csv_chunked() reads 100 rows at a time and passes each chunk to summarise_chunk(), keeping only its small result.

Combining the chunks

results              # one row per species per chunk
# A tibble: 6 × 3
  species   sum_mass     n
  <chr>        <dbl> <int>
1 Adelie      368225    99
2 Adelie      190575    52
3 Gentoo      241600    48
4 Chinstrap    88600    24
5 Gentoo      382750    75
6 Chinstrap   165250    44
results |>           # reduce: combine
  group_by(species) |>
  summarise(mean_mass = sum(sum_mass) / sum(n))
# A tibble: 3 × 2
  species   mean_mass
  <chr>         <dbl>
1 Adelie        3701.
2 Chinstrap     3733.
3 Gentoo        5076.

results has one row per species per chunk; the reduce adds up the sums and counts. This is reduce() with an .init accumulator from week 9, in disguise. Exactly the same code, with chunk_size = 50000, computes the mean fare per airport from the 29 GB file — the notes show the output; it takes a long time, so don’t run it live.

A chunking trap

Task

A file’s code column holds numbers for 15 rows, then codes like A1. We read it in chunks of 10 rows. What happens to the last five codes?

csv_text <- I(paste(
  c("id,code", paste0(1:20, ",", c(1:15, paste0("A", 1:5)))),
  collapse = "\n"
))
read_chunk <- DataFrameCallback$new(function(chunk, pos) chunk)
read_csv_chunked(csv_text, read_chunk, chunk_size = 10,
                 show_col_types = FALSE) |>
  tail(6)
# A tibble: 6 × 2
     id  code
  <dbl> <dbl>
1    15    15
2    16    NA
3    17    NA
4    18    NA
5    19    NA
6    20    NA

Column types are guessed from the first chunk only: code looks numeric, so later text becomes NA — silently. Always give col_types.

Wrap-up

Today you can now:

  • explain why data that doesn’t fit in memory breaks the usual workflow, and find the bottleneck
  • shrink the problem first: fewer columns, a subset, a better format
  • move the work: into a database (DuckDB, dbplyr), or into chunks (map-reduce), returning summaries that combine exactly
