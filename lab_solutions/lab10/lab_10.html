Task 1: Working in Chunks

The code below generates a large amount of dummy data for you to work with. It has two important parameters:

  • n: the number of rows
  • file_path: the path of the file written to

The data file contains four columns:

  • An id
  • A timestamp
  • A group (A, B, C or D)
  • A (numeric) value
Code 
set.seed(2025)

n <- 100000L  # data rows
if (!dir.exists("data")) dir.create("data")
file_path <- paste0("data/large_data_", n, ".csv")  # path to data

generate_data <- function() {
    group <- sample(c("A","B","C","D"), n, replace = TRUE, prob = c(0.4, 0.3, 0.2, 0.1))
    dat <- data.frame(
        id = seq_len(n),
        timestamp = as.POSIXct("2020-01-01", tz = "UTC") + runif(n, 0, 365*24*3600),
        group = group,
        value = rnorm(n, mean = 100, sd = 20) + as.numeric(factor(group, levels = c("A","B","C","D"))) * 2 + rnorm(n, 0, 1)
    )

    dat$value <- round(dat$value, 2)

    readr::write_csv(dat, file_path)
    message("Wrote ", nrow(dat), " rows to ", file_path)
}
if (!file.exists(file_path)) generate_data()

This data is big enough to give you an idea of how the tools work, but not big enough to be a problem. Task 2 uses a larger file to show what changes.

For this data, no. The whole file fits in memory many times over and loads in a fraction of a second, so read_csv() would be the right tool. We use chunks here to learn how they work; they pay off only when the data are too big to load.

The following code applies the map / reduce paradigm to sum a column in a “large” data file using readr::read_csv_chunked.

# Load required libraries
library(tidyverse)

# Define a callback function to process each chunk
process_chunk <- function(chunk, pos) {
  chunk |>
    summarize(chunk_sum = sum(value, na.rm = TRUE)) |>
    pull()
}

# Process data in chunks, with timing
start.time <- Sys.time()
# This performs the "map" step.
chunk_results <- read_csv_chunked(
  file_path,
  callback = DataFrameCallback$new(process_chunk),
  chunk_size = 1000
)

Modify the code above to answer the following questions:

Solution. Timings depend on your computer, but you should see the same pattern. On one run (median of five), the whole file took:

chunk_size 10 100 1000 10000 100000
Time (seconds) 0.45 0.04 0.03 0.04 0.15

Very small chunks are slow: with chunk_size = 10 the callback is called 10,000 times, and each call has a fixed cost (setting up the chunk, running the function, storing the result) that has nothing to do with how much data is in the chunk. Making the chunks bigger spreads this cost over more rows, which is why the time drops quickly between 10 and 1000.

But bigger is not always faster: the fastest value here is in the middle, and the single chunk of 100,000 rows (the whole file) was slower than 1000-row chunks. Since the point of chunking is to keep only one chunk in memory at a time, there is no benefit in making chunks larger than needed. A good chunk_size is large enough to make the per-chunk overhead small, and small enough that a chunk fits comfortably in memory. (With only 100,000 rows all of these are fast; the differences matter much more on a file with hundreds of millions of rows.)

For the questions, first we load the full dataset (for validation purposes) and define a generic function for the map / reduce.

full_data <- read_csv(file_path)

map_reduce_chunked <- function(file, map_op, reduce_op, chunk_size = 1000) {
    results <- read_csv_chunked(
        file,
        callback = DataFrameCallback$new(map_op),
        chunk_size = chunk_size
    )
    results |> reduce(reduce_op)
}

What is the sum of value for group A?

This is simple because we just need to filter.

map_a <- function(chunk, pos) {
    chunk |> filter(group == "A") |> summarise(value_sum = sum(value)) |> pull()
}

map_reduce_chunked(file_path, map_a, `+`)
[1] 4064210

What are the sums of value for each group?

This is more complex because the map step must now return a tibble, with one row per group, rather than a single number. By default, read_csv_chunked stacks the tibbles from all the chunks on top of each other. From this output it’s straightforward to use tidyverse functions to do the “reduce”: group again, and add up the partial sums.

map_group <- function(chunk, pos) {
    chunk |>
        group_by(group) |>
        summarise(value_sum = sum(value), .groups = "drop")
}

results <- read_csv_chunked(
    file_path,
    callback = DataFrameCallback$new(map_group),
    chunk_size = 1000
)
results |>
    group_by(group) |>
    summarise(value_sum = sum(value_sum), .groups = "drop")
# A tibble: 4 × 2
  group value_sum
  <chr>     <dbl>
1 A      4064210 
2 B      3120407.
3 C      2127435.
4 D      1079781.

Alternatively, we can write the reduce step ourselves, and pass it to reduce(). Now the callback has to return each chunk’s tibble inside a list(). Otherwise read_csv_chunked would stack the tibbles into one before reduce() sees it, and reduce() would try to combine the columns of that single tibble instead of the chunks. The reduce step takes the running total so far (cur) and the next chunk’s summary (new), stacks them and adds up again, so the result is always one row per group.

map_group_list <- function(chunk, pos) {
    list(
        chunk |>
            group_by(group) |>
            summarise(value_sum = sum(value), .groups = "drop")
    )
}

reduce_group <- function(cur, new) {
    bind_rows(cur, new) |>
        summarise(value_sum = sum(value_sum), .by = group)
}

map_reduce_chunked(file_path, map_group_list, reduce_group)
# A tibble: 4 × 2
  group value_sum
  <chr>     <dbl>
1 A      4064210 
2 B      3120407.
3 C      2127435.
4 D      1079781.

Stacking the two tibbles and summing again is safer than joining them by group. With an inner_join, any group missing from one chunk would be dropped altogether, which is quite possible with small chunks: with chunk_size = 10 an inner_join version returns no rows at all.

From here it is a simple extension to get the mean, by just adding the count of values to the summary. We must not return the mean of each chunk: means of chunks of different sizes can’t simply be averaged, but sums and counts can be added up exactly.

map_group_mean <- function(chunk, pos) {
    list(
        chunk |>
            group_by(group) |>
            summarise(value_sum = sum(value), value_count = n(), .groups = "drop")
    )
}

reduce_group_mean <- function(cur, new) {
    bind_rows(cur, new) |>
        summarise(
            value_sum = sum(value_sum),
            value_count = sum(value_count),
            .by = group
        )
}

mean_result <- map_reduce_chunked(file_path, map_group_mean, reduce_group_mean) |>
    mutate(mean = value_sum / value_count) |>
    select(group, mean)
mean_result
# A tibble: 4 × 2

Could you use this approach to compute the quantiles of value?

Not directly. The approach works for sums and means because the map step can return a small summary (a sum and a count) that combines exactly: adding up the summaries gives the same answer as if we had processed all the data at once. There is no small summary like this for a quantile. The median depends on where each value ranks among all the values, and knowing each chunk’s median doesn’t tell you that.

The obvious attempt is to take the median of each chunk’s median:

map_median <- function(chunk, pos) {
    tibble(chunk_median = median(chunk$value))
}

chunk_medians <- read_csv_chunked(
    file_path,
    callback = DataFrameCallback$new(map_median),
    chunk_size = 1000
)

median(chunk_medians$chunk_median)
[1] 103.9775
median(full_data$value)
[1] 103.99

This is close, but not equal, and nothing tells us how far off it is. Here the rows are in a random order, so every chunk looks like a small sample of the whole file; if the data were sorted or grouped in some way, the chunks would not be representative and the answer could be much worse. The map step can only return summaries that combine exactly, and for quantiles there aren’t any.

Task 2: Scaling Up

The file in Task 1 was small enough to read in a fraction of a second. In this task you will generate a larger file, and see which of the conclusions from Task 1 still hold.

Solution. With n set to 3000000L the file is about 111MB on disk, and about 92MB in memory as a tibble. That is still far from big for a modern computer, but it is large enough to see the effects.

On one run, the whole file took:

chunk_size 100 1000 10000 100000 1000000 3000000
Time (seconds) 4.6 1.0 1.0 1.1 3.2 9.0

The pattern is the same as before, but clearer. Small chunks are slow because of the overhead of each call, and a chunk of 1000 to 100,000 rows is fastest. Making the chunks larger again makes things slower: a single chunk containing the whole file (9.0 seconds) takes about nine times as long as read_csv() does on the same file (1.2 seconds). There is no benefit to large chunks, and a chunk that is too big is just the “load everything” approach with extra steps.

For the comparison:

Memory Speed (3M rows) Code
read_csv() The whole file, about 92MB here Fast, 1.2 s Simplest: ordinary dplyr
read_csv_chunked() One chunk at a time About 1 s with a sensible chunk_size, but much slower with a bad one Most work: we write the map and reduce steps, and the summaries must combine exactly

A 50GB file is too big for read_csv(), which needs to hold everything in memory at once. read_csv_chunked() needs only a single pass through the file, which at the speed of a solid-state drive takes a couple of minutes, and it can run any R code on each chunk, as long as we can combine the chunk results. The Week 10 notes describe a further option: letting a database such as DuckDB do the work, so that we write ordinary dplyr code and the database deals with the reading (see lab_10_practice.qmd). Either way, we would develop the code on a small subset first (n_max), as at the start of Task 1.
