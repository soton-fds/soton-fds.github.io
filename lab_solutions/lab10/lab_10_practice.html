Task 1: Standard Deviations from Chunks

Solution. The standard deviation is different from a quantile, because it can be built from summaries that do combine exactly. The variance of \(n\) values is \[ s^2 = \frac{1}{n - 1}\left(\sum_i x_i^2 - \frac{\left(\sum_i x_i\right)^2}{n}\right), \] so for each group, the map step only needs to return the sum of the values, the sum of their squares, and the count. All three can be added up across chunks, exactly as the sums and counts were for the mean.

map_group_sd <- function(chunk, pos) {
    list(
        chunk |>
            group_by(group) |>
            summarise(
                value_sum = sum(value),
                value_sq_sum = sum(value^2),
                value_count = n(),
                .groups = "drop"
            )
    )
}

reduce_group_sd <- function(cur, new) {
    bind_rows(cur, new) |>
        summarise(
            value_sum = sum(value_sum),
            value_sq_sum = sum(value_sq_sum),
            value_count = sum(value_count),
            .by = group
        )
}

sd_result <- map_reduce_chunked(file_path, map_group_sd, reduce_group_sd) |>
    mutate(
        variance = (value_sq_sum - value_sum^2 / value_count) / (value_count - 1),
        sd = sqrt(variance)
    ) |>
    select(group, sd) |>
    arrange(group)
sd_result

The two agree. (This formula can lose accuracy when the values are very large compared with their spread, because it subtracts two big numbers that are almost equal; it is fine for data like these.)

data |> summarize(value_sum=sum(value))

      <dbl>

Solution. This query is fine because it can be done in a single sweep.

data |> filter(group == "A") |> summarise(value_sum = sum(value))
# A duckplyr data frame: 1 variable
  value_sum
      <dbl>
1  4064210.

However, duckplyr refuses to run the group_by() version, because it would have to load the whole dataset into R to do so:

data |> group_by(group) |> summarise(value_sum = sum(value))
Error in `group_by()`:
! This operation cannot be carried out by DuckDB, and the input is a
  stingy duckplyr frame.
• Try `summarise(.by = ...)` or `mutate(.by = ...)` instead of `group_by()` and
  `ungroup()`.
ℹ Use `compute(prudence = "lavish")` to materialize to temporary storage and
  continue with duckplyr.
ℹ See `vignette("prudence")` for other options.

The error message suggests the fix: summarise() has a .by argument, which gives the same result as group_by() followed by summarise(), but which DuckDB can run.

data |> summarise(value_sum = sum(value), .by = group)
# A duckplyr data frame: 2 variables
  group value_sum
  <chr>     <dbl>
1 B      3120407.
2 A      4064210.
3 D      1079781.
4 C      2127435.

The data stay in DuckDB, which reads through the file once, and only the four-row result comes back to R.

The other route is to change prudence, which controls how willing duckplyr is to fall back on ordinary dplyr, and so to load the data into R’s memory. With "lavish" the grouped query runs, because duckplyr simply loads the whole dataset into memory, and then uses dplyr:

data_lavish <- read_csv_duckdb(file_path, prudence = "lavish")
data_lavish |> group_by(group) |> summarise(value_sum = sum(value))
# A tibble: 4 × 2
  group value_sum
  <chr>     <dbl>
1 A      4064210.
2 B      3120407.
3 C      2127435.
4 D      1079781.

The downside is that this is exactly the problem we were trying to avoid: for a file too big for memory, the query would fail or crash R. The default, "thrifty", is a middle ground: it only loads data into memory if they are small (fewer than a million cells). It happens to work here, because our file has only 100,000 rows of four columns, but it would give the same error as "stingy" on a genuinely large file. So the setting that “works” is only safe when the data are small enough that we didn’t need DuckDB in the first place.

Compared to read_csv_chunked, .by gives the same answer with no work on our part: we don’t have to write the map and reduce steps, or work out which summaries (sums and counts) can be combined. The cost is that it only works for the operations that DuckDB supports, whereas the chunked approach lets us run any R code on each chunk.

For the prudence experiment, the default prudence = "thrifty" now gives the same error as "stingy" for the grouped query, because the table is too big for duckplyr to be willing to load into memory. The query summarise(value_sum = sum(value), .by = group) still works. Only prudence = "lavish" would let group_by() through, by loading the whole file into memory. So the choice of prudence that “worked” on the small file was working only because the data were small.

Task 3: DuckDB with dbplyr

Solution. We connect to a temporary DuckDB database, and duckdb::tbl_file() gives a lazy table that reads directly from the CSV file, without loading it into R.

library(DBI)
library(dbplyr)

con <- dbConnect(duckdb::duckdb())
data_db <- duckdb::tbl_file(con, file_path)

query <- data_db |>
    group_by(group) |>
    summarise(value_sum = sum(value, na.rm = TRUE), .groups = "drop")

show_query(query)
<SQL>
SELECT "group", SUM("value") AS value_sum
FROM (FROM 'data/large_data_100000.csv') q01
GROUP BY "group"

The FROM clause names the CSV file itself, rather than a table in the database. Running the query gives the same sums as before:

query |> collect()
# A tibble: 4 × 2
  group value_sum
  <chr>     <dbl>
1 A      4064210.
2 C      2127435.
3 D      1079781.
4 B      3120407.
dbDisconnect(con)

The grouped query works because dbplyr never runs group_by() in R. It translates the whole pipeline into one SQL query, with a GROUP BY clause, and sends it to DuckDB, which reads through the file and returns only the four-row result. duckplyr instead tries to run each step itself, and when it meets a step it can’t run inside DuckDB (as with group_by()), it has to decide whether to load the data into R’s memory, which is what prudence controls. With dbplyr, there is no such decision to make: we have chosen to work in the database, so the query has to be one that SQL can express.
