Solution. Query C answers for each year, how many sets with at least 1,000 parts were released? WHERE is evaluated before GROUP BY, so it removes the smaller sets first, and the remaining large sets are then counted by year. Years with no large sets do not appear at all, so the result starts in 1985.

Query D answers in which years were at least 500 sets released, and how many? HAVING is evaluated after GROUP BY, so it keeps or removes whole years, based on the number of sets in each: only 2011–2016 pass.

Solution. Query E uses an inner JOIN, which keeps only the themes that match at least one set. A theme with no sets, such as Race, disappears from the result altogether, so the smallest count in Query E is 1.

Query F uses a LEFT JOIN, which keeps every theme. A theme with no sets is kept as a single row, with NULL in all of the columns from sets. But COUNT(*) counts rows, including that one, so Race is reported as having 1 set, just like Castle (id 25), which really does have one.

Query G also uses a LEFT JOIN, but COUNT(sets.set_num) counts only the rows in which set_num is not NULL, so Race correctly has 0 sets. Query G is the one your colleague wants.

SELECT name

    SELECT theme_id
    FROM sets

Solution. The first query answers which themes have no sets? The subquery lists the theme_id of every set, and the outer query keeps the themes whose id is not in that list. These are exactly the themes with n_sets equal to 0 in Query G; there are 39 of them.

The second query counts the themes that have no sets of their own (the first condition) and are the parent of at least one other theme (the second condition): 13 of the 39. For these themes, the sets are recorded under their sub-themes instead. The other 26 themes have no sets in this database at all.

Task 2: More of the LEGO Schema

This task follows on from the CREATE TABLE question in Task 1 of the lab. Here are the statements that were used to create three more of the tables.

CREATE TABLE themes (
    id INTEGER,
    name TEXT,
    parent_id INTEGER,
    PRIMARY KEY (id)
);

CREATE TABLE sets (
    set_num TEXT,
    name TEXT,
    year INTEGER,
    theme_id INTEGER,
    num_parts INTEGER,
    PRIMARY KEY (set_num),
    FOREIGN KEY (theme_id) REFERENCES themes(id)
);

CREATE TABLE colors (
    id INTEGER,
    name TEXT,
    rgb TEXT,
    is_trans TEXT,
    PRIMARY KEY (id)
);
SELECT is_trans, COUNT(*) AS n_colours
FROM colors
GROUP BY is_trans;
2 records
is_trans n_colours
f 107
t 28 
SELECT is_spare, COUNT(*) AS n_rows
FROM inventory_parts
GROUP BY is_spare;
2 records
is_spare n_rows
f 550574
t 29495

Solution. parent_id refers to the id of another row of the same table: for example, theme 220 (City) has parent 217 (Advent Sub-Set). This is a one-to-many relationship between themes and itself: one parent theme can have many sub-themes, but each theme has at most one parent. The schema figure in the lab does not show it.

The statement for themes declares no FOREIGN KEY (parent_id) REFERENCES themes(id), so nothing records that the two columns are linked, and a database that checks foreign keys could not stop a theme from having a parent that does not exist.

Both is_trans and is_spare hold the text 't' or 'f'. A BOOLEAN column would say what the columns mean and, in a database that checks types, stop other values (such as 'yes' or 'T') from creeping in. (SQLite is less strict about both types and foreign keys than most databases: see Using SQLite in the Week 7 notes.)

Task 3: Critiquing a Schema

This task follows on from Task 1 of the lab, but uses a different database. A small library has designed the database below, to record its members, its books and its loans.

CREATE TABLE members (
    member_id INTEGER,
    name TEXT,
    email TEXT,
    date_of_birth TEXT,
    PRIMARY KEY (member_id)
);

CREATE TABLE books (
    isbn TEXT,
    title TEXT,
    authors TEXT,  -- for example 'Wickham, H.; Grolemund, G.'
    year_published TEXT,
    price TEXT
);

CREATE TABLE loans (
    loan_id INTEGER PRIMARY KEY AUTOINCREMENT,
    member_id INTEGER,
    member_name TEXT,
    isbn TEXT,
    date_borrowed DATE,
    date_returned DATE,
    FOREIGN KEY (member_id) REFERENCES members(member_id)
);

Solution. There are several problems:

  • books has no primary key. The same book could be entered twice, and there is no way to identify a single book. isbn is a natural choice of key.
  • loans.isbn is not a foreign key. A loan could refer to a book that the library does not have. (It cannot be a foreign key at the moment, because a foreign key must refer to a primary key, and books does not have one.)
  • Wrong column types. year_published should be an INTEGER, price a REAL and date_of_birth a DATE. Stored as text, they cannot be sorted or compared correctly (as text, '9.99' sorts after '10.50'), and nothing stops values such as 'about 2010' from being entered.
  • loans.member_name repeats members.name. The name is stored again for every loan, and if a member changes their name, the two tables will disagree. It can always be found by joining loans to members, so it should be removed.
  • email is not UNIQUE. Two members could be registered with the same email address, which is probably a mistake (or the same person registered twice).
  • Copies. A library often has several copies of the same book, but a loan only records the ISBN, so we cannot tell which copy is on loan, or how many copies are available.

authors holds a list of names in a single column, which is not tidy (see the Week 4 notes): to find all the books by one author, we would have to search inside the text of every row. Books and authors are in a many-to-many relationship: a book can have several authors, and an author can write several books. As we saw for sets and parts in the lab, this needs an authors table, with one row per author, and a linking table book_authors, with one row for each author of each book.

name, email and date_of_birth are personal data, and are subject to data protection law (see the Week 7 notes and Data Ethics). The library needs a way to contact its members, but it is not clear that it needs their date of birth (unless, for example, children’s membership works differently), and it should not collect data it does not need. Staff issuing books need to see names; an analyst studying which books are popular needs none of these columns, and could be given only summaries.

For the extension, one possible design is:

CREATE TABLE members (
    member_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT,
    email TEXT UNIQUE
);

CREATE TABLE books (
    isbn TEXT PRIMARY KEY,
    title TEXT,
    year_published INTEGER,
    price REAL
);

CREATE TABLE authors (
    author_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT
);

CREATE TABLE book_authors (
    isbn TEXT,
    author_id INTEGER,
    PRIMARY KEY (isbn, author_id),
    FOREIGN KEY (isbn) REFERENCES books(isbn),
    FOREIGN KEY (author_id) REFERENCES authors(author_id)
);

CREATE TABLE copies (
    copy_id INTEGER PRIMARY KEY AUTOINCREMENT,
    isbn TEXT,
    FOREIGN KEY (isbn) REFERENCES books(isbn)
);

CREATE TABLE loans (
    loan_id INTEGER PRIMARY KEY AUTOINCREMENT,
    member_id INTEGER,
    copy_id INTEGER,
    date_borrowed DATE,
    date_returned DATE,  -- NULL if the copy has not been returned yet
    FOREIGN KEY (member_id) REFERENCES members(member_id),
    FOREIGN KEY (copy_id) REFERENCES copies(copy_id)
);

The primary key of book_authors combines both of its columns, like the key of inventory_parts in the lab: each pair of book and author should appear once.

Task 5: Theme Families

This task combines both tasks of the lab. In the lab, we found that counting sets by theme gives a misleading picture of which themes are the most popular, partly because large themes are split into many sub-themes.

Solution. For each theme, we look up its parent by joining themes to a copy of itself. Its family is its parent, if it has one, and otherwise the theme itself:

theme_family <- themes |>
    select(theme_id = id, parent_id) |>
    mutate(family_id = if_else(is.na(parent_id), theme_id, parent_id))

sets |>
    inner_join(theme_family, by = "theme_id") |>
    count(family_id) |>
    inner_join(themes |> select(family_id = id, family = name), by = "family_id") |>
    arrange(desc(n)) |>
    head(6) |>
    collect()
# A tibble: 6 × 3
  family_id     n family                 
      <int> <int> <chr>                  
1       217   625 Advent Sub-Set         
2       158   538 Star Wars              
3       443   455 Service Packs          
4       465   441 Universal Building Set 
5       535   441 Collectible Minifigures
6       501   433 Gear

We count by family_id rather than by name, because names are not unique, and only then join themes to itself to look up each family’s name.

Advent Sub-Set is a family of advent calendars, in which each day counts as a set, and Service Packs are spare parts, so the count of sets is still a poor measure of popularity. Star Wars, with over 500 sets, is the largest family of building sets here. We should not be very confident in any ranking, though: the counts measure how many products were released, not how many were sold, they depend on how the themes in the database have been organised, and the database contains no sales data at all.

For the extension, we join each theme to its parent and its grandparent, and check whether any grandparent has a parent of its own:

theme_levels <- themes |>
    select(theme_id = id, parent_id) |>
    left_join(
        themes |> select(parent_id = id, grandparent_id = parent_id),
        by = "parent_id"
    ) |>
    left_join(
        themes |> select(grandparent_id = id, great_grandparent_id = parent_id),
        by = "grandparent_id"
    )

theme_levels |>
    summarise(
        n_with_parent = sum(!is.na(parent_id), na.rm = TRUE),
        n_with_grandparent = sum(!is.na(grandparent_id), na.rm = TRUE),
        n_with_great_grandparent = sum(!is.na(great_grandparent_id), na.rm = TRUE)
    ) |>
    collect()
# A tibble: 1 × 3
  n_with_parent n_with_grandparent n_with_great_grandparent
          <int>              <int>                    <int>
1           503                156                        0

Some themes have a grandparent, but none has a great-grandparent, so themes are nested at most three levels deep. A theme’s top-level theme is therefore its grandparent if it has one, otherwise its parent if it has one, and otherwise the theme itself:

sets |>
    inner_join(theme_levels, by = "theme_id") |>
    mutate(
        top_id = case_when(
            !is.na(grandparent_id) ~ grandparent_id,
            !is.na(parent_id) ~ parent_id,
            TRUE ~ theme_id
        )
    ) |>
    count(top_id) |>
    inner_join(themes |> select(top_id = id, top_theme = name), by = "top_id") |>
    arrange(desc(n)) |>
    head(6) |>
    collect()
# A tibble: 6 × 3
  top_id     n top_theme             
   <int> <int> <chr>                 
1     50  1098 Town                  
2    206   923 Seasonal              
3    158   592 Star Wars             
4      1   533 Technic

Task 6: Checking the Data

This task follows on from Task 2 of the lab.

Solution. First, we add up the quantities in each set’s inventories, and compare the total with num_parts:

inventory_parts |>
    inner_join(inventories, by = c("inventory_id" = "id")) |>
    group_by(set_num) |>
    summarise(total = sum(quantity, na.rm = TRUE), .groups = "drop") |>
    inner_join(sets, by = "set_num") |>
    summarise(
        n_sets = n(),
        n_agree = sum(total == num_parts, na.rm = TRUE)
    ) |>
    collect()
# A tibble: 1 × 2
  n_sets n_agree
   <int>   <int>
1  10713    5811

Only about half agree. This total includes spare parts, which are not counted in num_parts. Leaving them out makes a big difference:

inventory_parts |>
    filter(is_spare == "f") |>
    inner_join(inventories, by = c("inventory_id" = "id")) |>
    group_by(set_num) |>
    summarise(total = sum(quantity, na.rm = TRUE), .groups = "drop") |>
    inner_join(sets, by = "set_num") |>
    summarise(
        n_sets = n(),
        n_agree = sum(total == num_parts, na.rm = TRUE)
    ) |>
    collect()
# A tibble: 1 × 2
  n_sets n_agree
   <int>   <int>
1  10710   10479

The total also adds up every inventory of a set, so a set with several inventory versions is counted several times. Keeping only the first version of each inventory removes this:

part_totals <- inventory_parts |>
    filter(is_spare == "f") |>
    inner_join(
        inventories |> filter(version == 1),
        by = c("inventory_id" = "id")
    ) |>
    group_by(set_num, inventory_id) |>
    summarise(total = sum(quantity, na.rm = TRUE), .groups = "drop") |>
    inner_join(sets, by = "set_num")

part_totals |>
    summarise(
        n_sets = n(),
        n_agree = sum(total == num_parts, na.rm = TRUE),
        n_fewer = sum(total < num_parts, na.rm = TRUE)
    ) |>
    collect()
# A tibble: 1 × 3
  n_sets n_agree n_fewer
   <int>   <int>   <int>
1  10709   10486     223

Now almost all of the sets agree. For every set that disagrees, the inventory lists fewer parts than num_parts. Some of these are sets that contain other sets, such as advent calendars, whose parts are listed in the inventories of the sets they contain (through inventory_sets), rather than in their own:

part_totals |>
    filter(total < num_parts) |>
    semi_join(inventory_sets, by = "inventory_id") |>
    count() |>
    collect()
# A tibble: 1 × 1
      n
  <int>
1    47

For the rest, the data do not tell us why the totals differ; most differ by only a few parts.
