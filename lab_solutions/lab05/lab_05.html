Each row of simpsons_script_lines is one line of a script, and each row of the other three tables is one character, location or episode. The script lines table is the “centre” that links the others: its episode_id, character_id and location_id columns refer to the id column of simpsons_episodes, simpsons_characters and simpsons_locations respectively. The other three tables are not linked to each other directly, so to connect, say, characters to locations, we have to go through the script lines.

Each link is one-to-many: an episode, character or location can appear in many script lines, but each script line has only one of each. For this to be true, each id must appear only once in its table, which we can check:

n_distinct(simpsons_episodes$id) == nrow(simpsons_episodes)
[1] TRUE
n_distinct(simpsons_characters$id) == nrow(simpsons_characters)
[1] TRUE
n_distinct(simpsons_locations$id) == nrow(simpsons_locations)
[1] TRUE

Notice also that some script lines have NA for character_id or location_id; these won’t match anything when we join.

Task 1b: Choosing a Join

All of the joins in Task 1 were inner joins, which keep only the rows that have a match in both tables. In this task we look at what that throws away.

Solution. How many rows does each join give?

nrow(simpsons_script_lines)
[1] 158255
simpsons_script_lines |>
    inner_join(simpsons_locations, by = c("location_id" = "id")) |>
    nrow()
[1] 157848
simpsons_script_lines |>
    left_join(simpsons_locations, by = c("location_id" = "id")) |>
    nrow()
[1] 158255

The left_join keeps every script line, but the inner_join has 407 fewer rows. Each location has a unique id, so a script line can match at most one location, and the inner_join must have dropped the lines that match no location.

What do the extra rows have in common?

simpsons_script_lines |>

    filter(is.na(location_name)) |>

There are 36 of them, and almost all are from the last few seasons in the data (26 to 28), so it looks as though the scripts for the most recent episodes were never added. This matters for our Task 1 answers: when we joined script lines to episodes, these episodes simply didn’t appear. Any conclusion about “the episodes” really only applies to the episodes with scripts.

Was inner_join the right choice?

Yes: the question is about pairs of a character and a location, so a line with no character or no location can’t contribute to any pair. Dropping those lines is exactly what we want. But it’s worth being aware that it happened: together, the two inner joins dropped almost 18,000 of the 158,255 lines. If instead we wanted, say, the total number of lines per character, a line with a missing location should still count, so we should either not join to the locations at all, or use a left_join.

No: after Homer’s line about the self-destruct code there is a newline, followed by what is clearly a whole row of a CSV file (140907,503,143,Robot: ...). Looking at the raw file, the spoken_words value for this line starts with a quotation mark (Homer is reading out a code) that is never closed. In a CSV file, text inside quotes may contain commas and even newlines, so read_csv keeps reading until it finds the next quotation mark, swallowing the following rows into this one value. Notice that read_csv gave no warning about this: the result has the right number of columns, so problems(simpsons_script_lines) is empty. Checking the extreme values of a column is a quick way to catch errors like this.

How many values have this problem? What is the genuine longest line?

Since each row of a CSV file ends with a newline ("\n"), any value containing one is suspicious:

simpsons_script_lines |>
    filter(str_detect(spoken_words, "\n")) |>
    nrow()
[1] 22

We remove these and look again. (Rows where spoken_words is NA are also dropped by this filter, since str_detect returns NA for them; that doesn’t matter here as they contain no words.)

simpsons_script_lines |>
    filter(!str_detect(spoken_words, "\n")) |>
    mutate(line_length = str_length(spoken_words)) |>
    arrange(desc(line_length)) |>
    head(1) |>
    inner_join(simpsons_episodes, by = c("episode_id" = "id")) |>
    select(title, line_length, spoken_words)
# A tibble: 1 × 3
  title                line_length spoken_words                                 
  <chr>                      <int> <chr>                                        
1 G.I. (Annoyed Grunt)         697 Frontline infantry. Absolutely Frontline inf…

Removing these values hides the damage, but doesn’t undo it. The rows that were swallowed are not in our data at all: the 22 broken values contain (parts of) 40 other rows, and by removing them we have also thrown away the 22 genuine lines they started with. Also, not every broken row contains a newline. For example, the row with id 152461 has its columns shifted, so its timestamp_in_ms, speaking_line, character_id and spoken_words are all NA. None of this changes our other answers much (it affects around 60 rows out of more than 158,000), but in a real analysis it would be worth repairing the file, or finding a better copy of the data.

In how many episodes are donuts / doughnuts mentioned?

Matching with str_detect is case-sensitive, so "donut" would not match “Donut” or “DONUTS”. We convert the text to lower case first (without this we would find only 52 episodes). A line can mention donuts more than once, and an episode can have many such lines, so we use distinct(episode_id) to count each episode once.

simpsons_script_lines |>
    mutate(lower_words = str_to_lower(spoken_words)) |>
    filter(str_detect(lower_words, "donut") | str_detect(lower_words, "doughnut")) |>
    distinct(episode_id) |>
    nrow()
[1] 56

Solution. Converting the text dates

Each column needs the function that matches the order of its day, month and year:

first_episodes |>
    mutate(
        from_uk = dmy(uk_date),
        from_us = mdy(us_date),
        from_long = mdy(long_date)
    ) |>
    select(title, from_uk, from_us, from_long)

Notice that mdy copes with the month written as a word: what matters is the order of the parts, not how they are written.

Solution. clean_names is in the janitor package, which we loaded in Task 3a. We overwrite stock_data with the cleaned version, so that we can use the new names from now on:

stock_data <- clean_names(stock_data)
names(stock_data)

Only Name has changed, to name. With so few columns this would be easy to fix by hand, but clean_names is a good habit: it deals with spaces, capitals and punctuation in one step, however many columns there are.

Answer the following research questions:

Solution. Which day of the year has the lowest trading volume on average?

stock_data |>
    mutate(day_of_year = yday(date)) |>
    group_by(day_of_year) |>
    summarise(mean_volume = mean(volume), .groups = "drop") |>
    arrange(mean_volume) |>
    head(1)
# A tibble: 1 × 2
  day_of_year mean_volume
        <dbl>       <dbl>
1         358    1675775.

Is a given day of the year always the same date?

No: 2016 is a leap year, so every date after 28 February is one day later in the year than usual.

yday(ymd(c("2015-12-24", "2016-12-24")))
[1] 358 359

So day 358 is 24 December in most years, but 23 December in 2016, and our answer above mixes up two different dates:

stock_data |>
    filter(yday(date) == 358) |>
    distinct(date)
# A tibble: 4 × 1
  date      
  <date>    
1 2013-12-24
2 2014-12-24
3 2015-12-24
4 2016-12-23

Grouping by month and day avoids this, and also gives an answer that is easier to read:

stock_data |>
    mutate(month = month(date), day = day(date)) |>
    group_by(month, day) |>
    summarise(mean_volume = mean(volume), .groups = "drop") |>
    arrange(mean_volume) |>
    head(1)
# A tibble: 1 × 3
  month   day mean_volume
  <dbl> <int>       <dbl>
1    12    24    1520642.

The answer is still 24 December, but the average volume is noticeably lower once 23 December 2016 is no longer included.

Why might this day have such a low trading volume?

24 December is Christmas Eve: US stock markets close early that day, and many traders are on holiday.
