  • Build and run a Shiny app from an R script.
  • Add input widgets (textInput, numericInput, selectInput) to an app, and display their values with output widgets and render functions.

About the Lab

In this lab you will write most of your code in R scripts, not in this Quarto document. As in the Week 8 notes, we always write Shiny apps in R scripts: a rendered Quarto document is a static web page, with no R process behind it to run an app. Write all your Shiny apps in the src/ subdirectory. Write your answers to the written questions in the solution boxes in this document.

To run an app, open its script in RStudio and click the Run App button above the editor (see Running Shiny Apps in the Week 8 notes). While the app is running, your R console is busy serving it: stop the app with the stop icon in the console (or Esc) to get your prompt back. A running app does not pick up changes to its script, so after editing an app, save it and click Run App again.

Task 1: A First App

Hint: Using renderUI to change greeting colour

To dynamically change the colour of the greeting based on the selected colour, use renderUI in the server and uiOutput in the UI. renderUI can return HTML tags such as span, whose style argument sets the CSS used to display it. For example, this displays some text in blue:

# In the ui:
uiOutput("coloured_text")

# In the server:
output$coloured_text <- renderUI({
  span(style = "color: blue;", "Some blue text")
})

Before a Name Is Entered

Solution. Before a name is entered, input$name is the empty string "", so the heading reads “’s Shiny App” and the greeting reads “Hello , it is great to know you are 21 years old!”.

req(input$name) treats "" as empty, and stops the reactive code it is in until a name has been entered:

output$title <- renderText({
  req(input$name)
  paste0(input$name, "'s")
})

greeting <- reactive({
  req(input$name)
  paste0(
    "Hello ",
    input$name,
    ", it is great to know you are ", input$age, " years old!"
  )
})

The heading’s textOutput is then blank, leaving just “Shiny App”. The best place for the greeting’s req() is inside the reactive expression greeting(), rather than in each output. When req() stops a reactive expression, every output that reads it is stopped too, so this one req() keeps both the plain and the coloured greeting blank.

The Reactive Graph

Now look at how the parts of your finished app depend on each other.

Solution. Your app may differ, but in the model solution (solutions/app1.R):

  • the sources are the three inputs, input$name, input$age and input$colour;
  • the only conductor is the reactive expression greeting(), which builds the greeting text from input$name and input$age;
  • the endpoints are the three outputs: output$title (which reads input$name), output$greeting (which reads greeting()) and output$coloured_greeting (which reads greeting() and input$colour).

Changing only the colour re-runs only output$coloured_greeting, since that is the only thing that reads input$colour. greeting() does not read the colour, so it is not out of date: output$coloured_greeting gets its cached value rather than rebuilding the text.

Changing only the name re-runs all three endpoints: output$title reads input$name directly, and both greetings read greeting(), which reads input$name. greeting() itself is recomputed only once: the first greeting to re-run recomputes it, and the second receives the cached result.

Task 2: A Data Visualiser

The file src/data/penguins.csv contains the penguins data from the Week 8 notes: body measurements of 344 penguins of three species, recorded on three islands in Antarctica between 2007 and 2009. Write a new app in src/ that is a flexible visualiser for this data.

As in the data explorer in the Week 8 notes, read the data once, before the ui, rather than inside the server. When Shiny runs an app, it uses the app’s own folder (here src/) as the working directory, so the app should read "data/penguins.csv", not "src/data/penguins.csv". (If you run the script line by line in the console instead, the working directory is the project folder, so the same path will not be found.)

The visualiser should allow the user to:

  • Select numerical variables for the \(x\) and \(y\) axes of a plot (using selectInput) and render the plot. Hint: a selectInput gives you a string, such as "bill_length_mm", rather than a column. Inside aes(), .data[[input$x_var]] refers to the column whose name is stored in input$x_var.
  • Select a categorical variable to use to colour the points on the plot.
  • Enter friendly \(x\)- and \(y\)-axis labels, and a title.
  • Create a reactive expression that filters the dataset based on another categorical variable.

Solution. By default, ggplot2 sets the axes to fit the points being plotted, so each species’ plot is rescaled to fill the panel. The Adelie plot’s body mass axis runs from about 2,750 g to 4,870 g, and the Gentoo plot’s from about 3,830 g to 6,420 g, so the two clouds of points look much the same. A reader who doesn’t check the axis labels could conclude that the species are a similar size, when Gentoo penguins are around 1.4 kg heavier on average, and have longer flippers.

As in the notes, coord_cartesian fixes the axes. The limits can’t be typed in, since they depend on which variables the user has chosen, but they can be computed from the whole dataset with range():

coord_cartesian(
  xlim = range(penguins[[input$x_var]], na.rm = TRUE),
  ylim = range(penguins[[input$y_var]], na.rm = TRUE)
)

penguins[[input$x_var]] extracts the column whose name is stored in input$x_var, as a vector. na.rm = TRUE is needed because each measurement is missing for two penguins. Now every plot of the same variables has the same axes, whichever species is chosen, so plots for different species can be compared directly.
