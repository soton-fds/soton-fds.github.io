7  SQL for Data Science

Objectives

  • Understand SQL as a declarative language for transforming data.
  • Be able to read and interpret SQL queries, including joins, GROUP BY aggregations and subqueries.
  • Appreciate the tradeoffs of doing computation in-database rather than in R.
  • Use dbplyr to query a database from R, and read the SQL that it generates.

7.1 What is a Relational Database?

A relational database is a structured collection of data organized into tables (also called relations). Each table consists of rows (records) and columns (fields), where each column has a specific data type and each row represents a single entry.

To draw analogies with data frames, each table is essentially a data frame. However, the data frames are linked through a key mechanism. Each table has a column that is referred to as a primary key which is like a unique identifier for the row. Often this is an integer, but it can be other things (e.g. a string, or a UUID). The important thing is that each value of a primary key can exist only once in the table, to ensure the row can be identified uniquely.

A table can also have foreign keys: columns whose values refer to primary keys in other tables, thus allowing for relations between the tables. If a column is labelled as a foreign key, consistency checks will be performed to ensure that the foreign key exists in the table it refers to.

7.1.1 Why use Relational Databases?

Relational databases offer several advantages:

  • Data Integrity: Enforce rules (such as primary and foreign keys) to maintain accurate and consistent data.
  • Scalability: Efficiently handle large volumes of data and complex queries.
  • Flexibility: Support powerful querying and data manipulation using SQL.
  • Security: Provide robust access controls and user permissions.
  • Redundancy Reduction: Minimize data duplication through normalization (i.e. breaking down the data into smaller, related tables rather than a single large table).
  • Concurrent Access: Allow multiple users to access and modify data safely at the same time.
  • Backup and Recovery: Offer built-in mechanisms for data backup and restoration.

7.2 What is SQL?

SQL (Structured Query Language) is a standardized language used to manage and manipulate relational databases. It allows users to define, query, update, and control access to data stored in tables. SQL is declarative, meaning you specify what data you want, not how to retrieve it. Common SQL operations include selecting data (SELECT), filtering (WHERE), joining tables (JOIN), aggregating results (GROUP BY), and modifying data (INSERT, UPDATE, DELETE). SQL is widely supported by database systems such as MySQL, PostgreSQL, SQLite, and Microsoft SQL Server, though there are some features that differ between implementations. In this course we will focus on sqlite, since it is widely available and does not require access to a server on which to host the database.

NoteUsing SQLite

In this chapter we describe how relational databases behave in general, as provided by database servers such as PostgreSQL or MySQL. SQLite supports all of the SQL in this chapter, but it is a deliberately lightweight system, and its behaviour differs from that of a database server in some places — for example, in how strictly it enforces some of the rules described here. More generally, every database system has its own dialect of SQL, so it is worth checking the documentation of the system you are using.

ImportantReading, not writing, SQL

In this course you will not be expected to write SQL yourself. You should, however, be able to read SQL: to interpret a query you are given, and explain what it does and what it returns (Section 7.2.5 gives a guide to doing this). When we work with databases from R, we will write dplyr code and let the dbplyr package translate it into SQL for us (see Section 7.3.1).

Much like R, SQL is typically written in plain text into text files, with the extension .sql. SQL is also stricter on formatting: a script containing several statements must separate them with semicolons (;), and it is good practice to end every statement with one.

7.2.1 Creating a SQLite DB

In this course you will mostly be supplied with pre-built SQLite databases to work with. There are various ways to create a database from scratch. One user-friendly way is using the DB Browser for SQLite. This gives the facility to create new databases and execute arbitrary SQL scripts on them, as well as interactive ways to create tables and insert data.

7.2.2 Creating Tables

The command for creating a table in a database is

    CREATE TABLE <table_name> (
        column_1 <column_1_type>,
        column_2 <column_2_type>, 
        ...,
        <constraints>
    )

It is idiomatic for keywords (e.g. CREATE TABLE) to be in all caps. Unlike R, the column types must be specified when the table is created, and the database checks that the values inserted into each column match its type.

The types that can be used vary between database systems, but most provide at least the following (sometimes under slightly different names):

  • INTEGER: a whole number.
  • REAL: a decimal number (called DOUBLE PRECISION or FLOAT in some systems).
  • TEXT: a text string (often VARCHAR).
  • BOOLEAN: true or false.
  • DATE and TIMESTAMP: dates, and dates with times.
  • BLOB: binary data (we won’t use these).

The examples in this chapter use only INTEGER, REAL and TEXT.

In addition to the type, a column can be designated as the table’s PRIMARY KEY, indicating that it contains the unique identifier for each row. A table has at most one primary key, but it can span several columns, when it is the combination of their values that identifies each row; this is written as a constraint, PRIMARY KEY (column_1, column_2), after the column definitions. We can further add the text AUTOINCREMENT after PRIMARY KEY to have the database generate new IDs automatically; this avoids having to check what the largest ID in a table is before inserting. (The keyword for this is one of the places where database systems differ: SQLite uses AUTOINCREMENT, while for example MySQL uses AUTO_INCREMENT.)

In addition to types, tables can also have constraints. Examples of constraints include:

  • UNIQUE: the column is not a primary key but each row can only contain unique values.
  • FOREIGN KEY: the column references the primary key in another table. The syntax for this differs, as we’ll see next.

The SQL examples in the rest of this section are run, in order, against a small SQLite database, so that you can see the result of each query beneath it.

Here is an example that creates three tables, each with a primary key: customers, products, and orders, which links the other two together through foreign keys.

-- Unlike R, comments in SQL start with two hyphens
-- Create customers table
CREATE TABLE customers (
    id INTEGER PRIMARY KEY AUTOINCREMENT, 
    first_name TEXT,
    last_name TEXT,
    email TEXT
);
-- Create products table
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    product_name TEXT,
    price REAL,
    stock INTEGER
);
-- Create orders table
CREATE TABLE orders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INTEGER,
    product_id INTEGER,
    quantity INTEGER,
    -- Constrain with two foreign keys:
    FOREIGN KEY (customer_id) REFERENCES customers(id),
    FOREIGN KEY (product_id) REFERENCES products(id)
);

Notice that the customers table holds personal data: names and email addresses. In a real database, data like this is subject to data protection law such as UK GDPR, which limits who may access it and what it may be used for (see Data Ethics); the access controls of a database server are one way of enforcing those limits.

WarningDropping Tables

We can also remove tables using the DROP TABLE syntax. This will delete all the data in the table, so should be used with care! A helpful command is DROP TABLE IF EXISTS which will drop the table only if it exists, otherwise do nothing.

7.2.3 Create, Read, Update and Delete

Once the table structure has been initialised, the four basic operations of persistent storage are Create, Read, Update and Delete (often abbreviated as CRUD).

7.2.3.1 Create

Inserting records into a table is accomplished with the INSERT command.

-- Insert data into customers table
-- Specifying the column names we want to insert into is good practice,
-- as it avoids a dependency on the order of database columns as well 
-- as allowing us to avoid needing to pass an ID.
INSERT INTO customers(first_name, last_name, email) VALUES
    ('Alice', 'Smith', 'alice.smith@email.com'), -- We don't need to pass an ID because of AUTOINCREMENT
    ('Bob', 'Jones', 'bob.jones@email.com'),
    ('Carol', 'Lee', 'carol.lee@email.com');
-- Insert data into products table
INSERT INTO products(product_name, price, stock) VALUES
    ('Widget', 19.99, 10),
    ('Gadget', 29.99, 5),
    ('Thingamajig', 9.99, 2);
-- Insert data into orders table
INSERT INTO orders(customer_id, product_id, quantity) VALUES
    (1, 2, 1),
    (1, 3, 2),
    (2, 1, 2),
    (2, 2, 4),
    (3, 3, 1);

We can read from a table using the SELECT command.

-- sort products by price, most expensive first

ORDER BY sorts the rows by one or more columns, in ascending order unless the column is followed by DESC. Without an ORDER BY, the database makes no promise about the order in which it returns rows. DISTINCT removes duplicate rows from the result: each customer appears once, however many orders they have placed.

We can also directly JOIN tables using SQL, to produce more complex queries.

SELECT -- specify columns to select
    orders.id,
    products.product_name,
    orders.quantity,
    customers.first_name,
    customers.last_name
FROM orders -- the table to start from
    -- each JOIN adds a table, with ON saying how its rows match
    JOIN customers ON orders.customer_id = customers.id
    JOIN products ON orders.product_id = products.id;
5 records
id product_name quantity first_name last_name
1 Gadget 1 Alice Smith
2 Thingamajig 2 Alice Smith
3 Widget 2 Bob Jones
4 Gadget 4 Bob Jones
5 Thingamajig 1 Carol Lee

Each JOIN adds one table to the query, and its ON condition says which of the new table’s rows match each existing row: here, each order is matched to the customer who placed it and the product that was ordered. Because the tables contain columns with the same names (all three have an id), each column is written as table.column to make clear which table it comes from.

TipJoin Types

The other join types we saw in Week 5 also exist in SQL. The syntax JOIN is a shorthand for INNER JOIN, while LEFT JOIN, RIGHT JOIN and FULL OUTER JOIN are the equivalents of left_join, right_join and full_join. (OUTER JOIN on its own is not valid: you must say which kind of outer join you mean.)

7.2.3.3 Update

Updating records is accomplished with the UPDATE command:

-- Update the price of a product
UPDATE products
SET price = 24.99
WHERE product_name = 'Gadget';
-- Update the stock for a specific product
UPDATE products
SET stock = stock + 5
WHERE id = 1;
-- Update a customer's email address
UPDATE customers
SET email = 'alice.new@email.com'
WHERE id = 1;

7.2.3.4 Delete

As you might expect, deleting is accomplished with DELETE.

-- Delete a specific order by id
DELETE FROM orders
WHERE id = 3;
-- Delete all products with zero stock
DELETE FROM products
WHERE stock = 0;
-- Delete a customer by email
DELETE FROM customers
WHERE email = 'bob.jones@email.com';

7.2.4 Advanced Queries

Beyond reading, filtering and joining tables, SQL has some more advanced syntax that is useful for particular kinds of query.

7.2.4.1 Aggregation

We can perform aggregation using the GROUP BY statement, which is the analogue of group_by in dplyr. This allows us to lump multiple records into a group and specify how they should be aggregated. Some example statements are given below. The first counts the total number of orders for each customer.

-- Count orders per customer
SELECT customer_id, COUNT(*) as order_count
FROM orders
GROUP BY customer_id;
3 records
customer_id order_count
1 2
2 1
3 1

The syntax COUNT(*) specifies a calculated column: the number of rows in each group defined by the GROUP BY statement. COUNT(*) counts every row, whereas COUNT(column_name) counts only the rows in which that column is not missing (NULL).

The next statement calculates total revenue for each product.

-- Total revenue per product
SELECT product_id, product_name, SUM(quantity * price) AS total_revenue
FROM orders
JOIN products
    ON orders.product_id = products.id
GROUP BY product_id, product_name;
2 records
product_id product_name total_revenue
2 Gadget 124.95
3 Thingamajig 29.97

SUM(quantity * price) specifies that we should calculate quantity * price for each order, and then SUM over the groups specified. AS gives the calculated column a name. Notice that product_name appears in the GROUP BY as well as product_id: every column in the SELECT must either be grouped by, or be calculated by an aggregate function such as SUM or COUNT. (Here each product_id has a single product_name, so grouping by both gives the same groups as grouping by product_id alone.)

7.2.4.2 Subqueries

Sometimes we might not be able to compute a table of interest using a single query; we might need to perform two queries to accomplish this. For example, if we want to view the details of customers who have placed more than one order, we first need to execute a query on the orders table to identify those customers, then filter the customers table based on the IDs. To accomplish this we can use subqueries, to nest the orders query inside another query.

-- Find customers who have placed more than one order
SELECT first_name, last_name
FROM customers
WHERE id IN (
    SELECT customer_id
    FROM orders
    GROUP BY customer_id
    HAVING COUNT(*) > 1
);
1 records
first_name last_name
Alice Smith

Note that this introduces the HAVING syntax for GROUP BY also, allowing us to filter groups, as well as the IN syntax for specifying a list of IDs to compare to, rather than a single ID.

The next query identifies products that have never been ordered, again by querying the orders table first.

-- Find products that have never been ordered
SELECT product_name
FROM products
WHERE id NOT IN ( -- NOT IN also works!
    SELECT product_id
    FROM orders
);
1 records
product_name
Widget

7.2.4.3 Missing Values

Missing values are represented in SQL by NULL, the equivalent of NA in R (see Week 2). Like NA, NULL means “unknown”, so any comparison with it is also unknown: a condition such as email = NULL is never true, and a WHERE clause using it keeps no rows at all. To test whether a value is missing, use IS NULL or IS NOT NULL instead:

-- customers with no email address recorded
SELECT first_name, last_name
FROM customers
WHERE email IS NULL;
0 records
first_name last_name

Every customer in our small database has an email address, so this query returns no rows.

Aggregate functions such as SUM and AVG skip NULLs, as if na.rm = TRUE had been set in R; so does COUNT(column_name), whereas COUNT(*) counts every row.

7.2.5 Reading SQL Queries

You will have noticed that most SQL clauses have a direct counterpart in dplyr, which we met in Week 4 and 5:

SQL dplyr
FROM table the data frame at the start of the pipe
JOIN other ON ... inner_join(other, by = ...)
LEFT JOIN other ON ... left_join(other, by = ...)
WHERE condition filter(condition)
GROUP BY column group_by(column)
COUNT(*), SUM(x), AVG(x), … n(), sum(x), mean(x), …, inside summarise()
HAVING condition filter(condition) after summarise()
SELECT column_1, column_2 select(column_1, column_2)
expression AS name mutate(name = expression), or name = expression inside summarise()
DISTINCT distinct()
ORDER BY column DESC arrange(desc(column))
LIMIT n head(n)
column IS NULL is.na(column)

The main difference is in the order of the steps. A dplyr pipeline is written in the order in which it runs, from top to bottom. A SQL query is always written in the same fixed order, beginning with SELECT, but the database evaluates its clauses in a different order:

  1. FROM and JOIN: assemble the rows from the tables.
  2. WHERE: keep only the rows that satisfy the condition.
  3. GROUP BY: split the remaining rows into groups.
  4. HAVING: keep only the groups that satisfy the condition.
  5. SELECT: compute the columns of the result, including aggregates such as COUNT(*).
  6. DISTINCT: remove duplicate rows.
  7. ORDER BY: sort the result.
  8. LIMIT: keep only the first few rows.

To read a query, therefore, start at FROM rather than at SELECT. For example, this query

SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE quantity >= 2
GROUP BY customer_id
HAVING COUNT(*) > 1
ORDER BY order_count DESC
LIMIT 5;

reads, in evaluation order: take the orders table; keep the orders of at least two items; group them by customer; keep the customers with more than one such order; for each, report the customer’s ID and their number of orders; sort with the most orders first; and keep the top five. In dplyr, the same steps appear in the same order:

orders |>
    filter(quantity >= 2) |>
    group_by(customer_id) |>
    summarise(order_count = n()) |>
    filter(order_count > 1) |>
    arrange(desc(order_count)) |>
    head(5)

The evaluation order also explains some of SQL’s rules. WHERE filters individual rows before they are grouped, so it cannot refer to aggregates such as COUNT(*); that is the job of HAVING, which filters the groups afterwards. Similarly, in most databases a name defined with AS in the SELECT can be used in ORDER BY, which comes later, but not in WHERE, which comes earlier.

dbplyr, which we meet below, does this translation in the other direction: it turns a dplyr pipeline into SQL, which we can read using the same approach.

7.3 Why Use SQL vs. R

You will by now have noticed that SQL can do much of what we learned to do with dplyr in Weeks 4–5 (see Section 7.2.5). We discussed the advantages of a database for storing data in Section 7.1.1. This section is about a different question: once the data are stored in a database, where should the work of filtering, joining and summarising them be done? There are two options:

  • run the query in the database, and import only its result into R; or
  • import the tables into R, and run the query there using dplyr.

Doing the work in the database has several advantages:

  • Less data to transfer. Only the result of the query leaves the database. A summary of a table with millions of rows might be a handful of rows, so moving it to R is far quicker than moving the table itself, particularly when the database is on a remote server.
  • Data larger than memory. R holds the data it works on in memory, whereas a database works with data stored on disk, so it can process tables far too large to load into R at all. In Week 10 we will meet DuckDB, a database designed for analysing large datasets, which can even run queries directly on CSV files stored on disk, using the same dplyr verbs.
  • Speed. Databases are designed for exactly these operations. They plan how to carry out each query efficiently, can use indexes to find matching rows without reading the whole table, and often run on a server more powerful than your own computer.
  • Privacy. If only summaries leave the database, sensitive individual-level data, such as the names and email addresses in our example, never need to be copied onto your computer. Combined with the access controls of a database server, this can make it much easier to handle personal data responsibly (see Data Ethics).

Doing the work in R has advantages too:

  • Expressiveness. R can do far more than SQL: statistical modelling, visualisation, and the many functions provided by R packages. As we will see in Section 7.3.1, only some R functions can be translated into SQL.
  • Simplicity for small data. If a table fits comfortably in memory, it is often simpler to import it once and work with it in R, rather than querying the database again for every change to the analysis.

In practice, the two are usually combined: the database does the filtering, joining and summarising that reduce the data to what the analysis needs, and R does the rest. Whichever you choose, the query is part of your analysis, so it belongs in your code, alongside the rest of the analysis, rather than being run separately by hand: this keeps the whole analysis reproducible (Chapter 3). dbplyr, which we turn to next, makes this especially convenient, because the boundary between the two becomes a single call to collect().

7.3.1.1 Using dbplyr Well

Because dbplyr translates our code into SQL, rather than running it in R, there are a few things to bear in mind.

Call collect() as late as possible. Everything before collect() runs in the database, and only its result is sent to R; everything after it runs in R, on data that has already been transferred. These two pipelines give the same result:

# filter in the database: only the matching rows are sent to R
orders |> filter(quantity >= 3) |> collect()

# filter in R: the whole table is sent to R first
orders |> collect() |> filter(quantity >= 3)

but the first sends R only the matching orders, while the second transfers the entire orders table before discarding most of it. On a table this small the difference is negligible; on one with millions of rows, it is the difference between a query that finishes in seconds and one that does not fit in memory.

Only functions that dbplyr knows how to translate can be used before collect(). dbplyr translates common functions, such as the arithmetic operators, mean(), n() and paste(), into their SQL equivalents. Functions without an equivalent in the database’s SQL cannot be translated, and cause an error:

customers |>
    mutate(padded_name = stringr::str_pad(first_name, 10)) |>
    collect()
Error in `stringr::str_pad()`:
! `str_pad()` is not available in this SQL variant.

The fix is to do as much work as possible in the database, then collect() the result and use the function in R afterwards.

A lazy table can only be joined to another table in the same database. Joining it to a tibble that lives in R fails:

vip_customers = tibble(id = c(1, 4), level = c("gold", "silver"))

customers |> inner_join(vip_customers, by = "id")
Error in `auto_copy()`:
! `x` and `y` must share the same src.
i `x` is a <tbl_SQLiteConnection/tbl_dbi/tbl_sql/tbl_lazy/tbl> object.
i `y` is a <tbl_df/tbl/data.frame> object.
i Set `copy = TRUE` if `y` can be copied to the same source as `x` (may be
  slow).

As the error message suggests, adding copy = TRUE copies the tibble into a temporary table in the database, after which the join can run there:

customers |>
    inner_join(vip_customers, by = "id", copy = TRUE) |>
    collect()
# A tibble: 2 x 5
     id first_name last_name email                    level 
  <int> <chr>      <chr>     <chr>                    <chr> 
1     1 David      Brown     david.brown@example.com  gold  
2     4 Grace      Wilson    grace.wilson@example.com silver

For a small tibble like this one, copying is cheap; for a large one, it may be better to collect() the database table first, if it is small enough, and join in R.

Finally, we close the connection to the database once we have finished with it:

dbDisconnect(con)
