7  Introduction to Shiny

Objectives

  • Know what shiny is and what problems it solves.
  • See how a basic shiny app is structured and executed.
  • Be able to describe reactive programming at a high level.
  • Recognise common use cases for shiny, and its limitations.
  • Recognise the most common input, output and layout components, and know where to look up the rest.

7.1 What is Shiny?

Shiny is an R package that makes it easy to build interactive web applications directly from R. Developed by RStudio (now Posit), Shiny allows users to turn analyses into interactive dashboards and tools without requiring knowledge of HTML, CSS, or JavaScript.

Shiny apps are especially useful for sharing data analyses with others, enabling users to explore data and results dynamically through a web browser. This interactivity helps bridge the gap between static reports and fully custom web applications.

Key features of Shiny include:

  • Seamless integration with R code and packages.
  • Automatic UI updates in response to user input.
  • Support for a wide range of input and output widgets.
  • Ability to deploy apps locally or on the web (e.g., via shinyapps.io or Shiny Server).

shiny is not part of tidyverse; it is a separate package that must be installed on its own, and loaded with library(shiny) at the top of every app script.

TipInstalling Shiny

Run install.packages("shiny") once in your R console, then load it in each session with library(shiny). Since Shiny apps cannot run from .qmd files anyway (see below), there is no risk of re-installing the package on every render.

7.2 Basic Structure of a Shiny App

A basic Shiny app consists of two main components:

  • UI (User Interface): Defines the layout and appearance of the app.
  • Server: Contains the instructions for how the app responds to user input.

Here is a minimal example of a Shiny app:

library(shiny)

ui <- fluidPage(
  titlePanel("Hello Shiny!"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("num", "Choose a number:", 1, 100, 50)
    ),
    mainPanel(
      textOutput("result")
    )
  )
)

server <- function(input, output, session) {
  output$result <- renderText({
    paste("You selected:", input$num)
  })
}

shinyApp(ui, server)

The variable ui describes a simple user interface. The code entered into fluidPage is translated into an HTML page (styled using the bootstrap CSS library) when the app starts. The variable server describes the “back-end”: a function that connects the inputs defined in the UI to the outputs displayed in it. It takes three arguments — input and output make the values described below available to the server, and session is an advanced object we will not use (it can be omitted).

The two ends of the app are tied together by the names given to components. The slider above was declared with sliderInput("num", ...): the string "num" is the slider’s name, and its current value can be read in the server as input$num. Likewise, textOutput("result") reserves a display slot named "result", which the server fills in by assigning to output$result — here using renderText. Pairing names in this way is the backbone of every shiny app: the input names determine what input$... contains, and the output names must match the output$... assignments. A reference table of output components and their matching render functions appears in Section 7.5.

When the user changes something in the UI, the server function is not re-run; instead, shiny re-runs only the reactive code registered inside it — here, the renderText block — when the values it depends on (here input$num) change. This is the reactive programming model we describe in the sections below.

7.3 How Shiny Apps are Executed

A static Quarto document such as this book cannot host a running web server, so Shiny apps need to be written in R scripts. The usual convention is a single script named app.R that defines ui and server and ends with a call to shinyApp, sometimes kept in a folder of its own with any data files alongside (app.R and ui.R/server.R splits are also common). There are several ways to run Shiny apps in development:

  1. In an interactive session, having defined ui and server, type the code shinyApp(ui, server).
  2. Save the app as app.R and run it through the shiny function runApp — for example, runApp() if you are working in the app’s folder, or runApp("path/to/app") otherwise.
  3. Clicking the “Run App” button that appears in RStudio when you open a Shiny app file.

In all of the above, Shiny will start a web server on your computer. You should see an output that looks like:

Listening on http://127.0.0.1:3689
Browsing http://127.0.0.1:3689

This gives you a URL that you can enter into your browser to interact with the app. In RStudio the app will be opened automatically in a new window. While the app is running, your R console is busy serving it: stop the app (the stop icon in RStudio, or Esc in the console) to get your prompt back before continuing to work.

The execution flow is as follows:

  1. Initialization: The UI is generated and displayed in the browser.
  2. User Interaction: When a user interacts with an input (e.g., moves a slider), the browser sends the new input value to the server.
  3. Reactivity: The server detects which outputs depend on the changed input and recalculates them.
  4. Output Update: The updated outputs are sent back to the browser and displayed instantly.

You can run Shiny apps:

  • Locally: Directly from your R session, accessible only on your machine.
  • Remotely: By deploying to a server (e.g., shinyapps.io), making the app accessible to others via a web link.

This architecture allows for real-time, interactive data exploration without requiring users to install R or any packages.

7.4 Reactive Programming

Reactive programming is a programming paradigm centred around the propagation of changes. In Shiny, this means that outputs automatically update in response to changes in inputs, without the need for explicit instructions to recalculate or redraw.

Shiny achieves this through a system of “reactive expressions” and “reactive values.” When a user interacts with an input widget (like a slider or text box), Shiny tracks which outputs depend on that input. Only the affected outputs are recalculated and updated, making the app efficient and responsive.

Key concepts in Shiny’s reactive programming:

  • Inputs: User interface elements that collect information from the user (e.g., sliders, text boxes).
  • Outputs: UI elements that display results or visualizations, updated automatically when their dependencies change.
  • Reactive expressions: Special functions (created with reactive()) that cache their results and only re-execute when their inputs change.
  • Observers: Code blocks (created with observe() or observeEvent()) that perform actions in response to changes, such as updating UI elements or triggering side effects.

We have already seen inputs and outputs; now we will talk about reactive expressions and observers.

7.4.1 Reactive Expressions

Reactivity in Shiny is the mechanism by which code automatically updates when inputs, or other reactive values, change. In the previous code block we already used a reactive function: renderText. This ensures that the renderText block — and with it the text displayed in the UI — is re-run whenever input$num changes. In the background, R is building a graph of dependencies on values from the UI, and updates only the appropriate parts of the server logic when the dependencies change.

There are multiple other reactive functions:

  • reactive({...}): define a reactive expression that can be re-used in multiple places.
  • reactiveVal: define new reactive values that you can then get or set.
  • reactiveValues(): define a whole list of new reactive values that you can read and set like input (e.g. values$x).
  • renderText, renderPlot, renderTable, renderUI: create outputs for the UI, one for each type of *Output component (see Section 7.5).

Two things to watch out for when you use reactive: its result is retrieved by calling it like a function — data(), not data — and, like other reactive values, it can only be read inside reactive code (see the warning below).

Here is an example in which we use reactive and renderPlot to make more complex logic.

library(shiny)
library(tidyverse)

ui <- fluidPage(
  fluidRow(
    column(
      2,
      numericInput("mu1", label = withMathJax("$$\\mu_1$$"), value = -1, width="80px")
    ),
    column(
      2,
      numericInput("mu2", label = withMathJax("$$\\mu_2$$"), value = 1, width="80px")
    )
  ),
  plotOutput("plot")
)

server <- function(input, output, session) {
  data <- reactive(tibble(
    x1 = rnorm(500, input$mu1, 1), 
    x2 = rnorm(500, input$mu2, 1))
  )
  output$plot <- renderPlot(
    {
      ggplot(data(), aes(x = x1, y = x2)) +
        geom_point() +
        coord_cartesian(xlim = c(-5, 5), ylim=c(-5, 5))
    },
    res = 96
  )
}

shinyApp(ui, server)

A few details in this example are worth a second look:

  • withMathJax renders its argument as LaTeX, so the input labels display properly as \(\mu_1\) and \(\mu_2\).
  • data is a reactive expression, so renderPlot must call it — data() — rather than referring to it as a plain variable.
  • coord_cartesian(xlim = c(-5, 5), ylim = c(-5, 5)) fixes the axes rather than letting ggplot2 rescale to whatever data is currently displayed; without it, the visible area would jump around with every change to the inputs.
  • res = 96 sets the resolution (pixels per inch) of the rendered plot image.
WarningReactive values can only be read inside reactive code

Values like input$mu1 and calls to reactive expressions like data() may only be read inside reactive code — that is, inside reactive, render*, observe or observeEvent blocks. Reading them anywhere else (for example, directly in the body of server) triggers an error telling you that the read is only allowed inside a reactive context. Inputs also cannot be overwritten from the server: assigning to input$mu1 fails, because inputs are set by the user through the UI. If you need a value the server can change, use reactiveVal or reactiveValues.

7.4.2 Observers

Observers are another way to introduce reactivity. Whereas reactive statements typically return values and are designed to give reusable expressions, observe statements do not return values, and are used when one might want to run code with side effects (e.g. for logging) or to trigger UI updates manually.

The two main observer functions are:

  • observe({...}): triggers if any reactive value inside the block changes
  • observeEvent(event, {...}): explicitly triggered only by the event specified.

Here’s an example showing how observeEvent can be used to run code on button clicks. Button presses are the classic case for observers: an actionButton does not hold a value you would want to display — each press is an event to respond to — so buttons are usually paired with observeEvent rather than used inside render* functions.

library(shiny)

ui <- fluidPage(
  actionButton("inc", "Increase counter"),
  actionButton("reset", "Reset counter"),
  textOutput("value")
)

server <- function(input, output, session) {
  # Create a reactiveVal starting at 0.
  # Retrieve its value by calling it, counter(); set it by calling it with an
  # argument, counter(new_value).
  counter <- reactiveVal(0)

  # Increase counter when 'inc' button is clicked
  observeEvent(input$inc, {
    counter(counter() + 1)   # update value
  })

  # Reset counter when 'reset' button is clicked
  observeEvent(input$reset, {
    counter(0)
  })

  # Display the current value
  output$value <- renderText({
    paste("Counter is:", counter())   # read value
  })
}

shinyApp(ui, server)

7.5 Common Components

Shiny provides a large collection of UI components; this section is a quick reference to the ones you are most likely to need in this course, ending with a worked example that combines several of them. The naming contract from the first example applies throughout: an input component’s first argument is its name, and its current value can then be read in the server as input$name; an output component’s name must match the output$name assignment that fills it. For components not listed here, the widget gallery has a live, runnable example of every input widget, the Shiny gallery showcases complete apps, and the Shiny cheat sheet condenses the essentials onto two pages; Winston Chang’s free online book Mastering Shiny is the standard in-depth reference.

7.5.1 Layout Functions

These components control the structure of the page. Every app has a fluidPage at its root.

Function Purpose
fluidPage(...) The root of the UI: a page whose rows and columns adapt to the width of the screen.
titlePanel("...") Displays a title at the top of the page.
sidebarLayout(sidebarPanel(...), mainPanel(...)) The classic layout: a narrow panel of controls beside a wide panel of results.
fluidRow(...) A row spanning the page, holding one or more columns.
column(width, ...) A column within a fluidRow. width runs from 1 (narrow) to 12 (the full page).
tabsetPanel(tabPanel("A", ...), tabPanel("B", ...)) Splits content across tabs that the user switches between.
conditionalPanel(condition, ...) Displays its contents only while condition — a JavaScript string such as "input.choice != ''" — holds.
wellPanel(...) A bordered, grey panel that visually groups other components.
helpText("...") Small, low-contrast explanatory text.

7.5.2 Input Widgets

Input widgets are placed in the UI, and their current values are read in the server through input$<name>.

Widget Collects Notes
sliderInput(id, label, min, max, value) A number, by dragging a slider Doubles as a range slider — see the callout below.
selectInput(id, label, choices) One choice from a dropdown choices is a character vector; giving its entries names (e.g. c("(Choose a species)" = "")) displays the name while input$<id> takes the value. A named empty entry like the one shown is the standard way to represent “nothing chosen yet”.
numericInput(id, label, value) A number, typed Optional min, max and step control the attached arrows.
textInput(id, label) A string, typed
checkboxInput(id, label) A single tick-box input$<id> is TRUE or FALSE.
checkboxGroupInput(id, label, choices) Any number of tick-boxes input$<id> is a character vector of the ticked values.
radioButtons(id, label, choices) Exactly one of several options Like a selectInput, but with all choices visible at once.
dateInput(id, label) A single date A Date value.
dateRangeInput(id, label) A start and end date A Date vector of length two, so index it as input$<id>[1] and input$<id>[2].
actionButton(id, label) Button presses A press is an event to respond to with observeEvent, not a value to display.
TipRange sliders

Passing a length-two value to sliderInput produces a double-ended slider with which the user selects a range:

sliderInput(
  "years",
  "Release years:",
  min = 1960,
  max = 2024,
  value = c(1960, 2024),
  sep = ""
)

The server then sees a vector of two numbers: input$years[1] is the lower end of the range and input$years[2] the upper, so filter(year >= input$years[1], year <= input$years[2]) selects the rows falling inside it. (sep = "" just removes the thousands-separating comma from the numbers displayed on the slider.)

7.5.3 Output Widgets and Render Functions

Every output widget in the UI is filled in by a matching render function assigned in the server: output$name <- renderPlot({...}) pairs with plotOutput("name"). These are the common pairs.

In the UI In the server Displays
textOutput(id) renderText({...}) A character string.
verbatimTextOutput(id) renderPrint({...}) Whatever printing produces, as fixed-width console-style text — handy for str() output or a fitted model.
plotOutput(id) renderPlot({...}) Any plot, including ggplot2 plots.
tableOutput(id) renderTable({...}) A data frame, as a static table.
DT::dataTableOutput(id) DT::renderDataTable({...}) A data frame as a large, sortable, searchable table. DT is a separate package (install.packages("DT")).
uiOutput(id) renderUI({...}) UI components that are constructed dynamically in the server.

7.5.4 Example: A Small Data Explorer

The app below combines several of the components above — a dropdown with a placeholder choice, a range slider and a tick-box on the input side; a plot and a table on the output side. It follows the usual convention for loading data: read_csv is called once, before the app starts, rather than inside the server, so that the file is not re-read every time an input changes.

library(shiny)
library(tidyverse)

# Read the data once, when the app starts (not inside the server).
penguins <- read_csv("data/penguins.csv")

ui <- fluidPage(
  titlePanel("Penguin explorer"),
  sidebarLayout(
    sidebarPanel(
      selectInput(
        "species",
        "Choose a species:",
        choices = c("(Choose a species)" = "", "Adelie", "Gentoo", "Chinstrap")
      ),
      sliderInput(
        "mass",
        "Body mass (g):",
        min = 2700,
        max = 6300,
        value = c(2700, 6300),
        sep = ""
      ),
      checkboxInput("trend", "Show a trend line", value = TRUE)
    ),
    mainPanel(
      plotOutput("plot"),
      tableOutput("table")
    )
  )
)

server <- function(input, output, session) {
  selected <- reactive({
    penguins |>
      filter(
        species == input$species,
        body_mass_g >= input$mass[1],
        body_mass_g <= input$mass[2]
      )
  })

  output$plot <- renderPlot({
    req(input$species)   # do nothing until a species is chosen
    plot <- ggplot(selected(), aes(x = flipper_length_mm, y = body_mass_g)) +
      geom_point()
    if (input$trend) {
      plot <- plot + geom_smooth(se = FALSE)
    }
    plot
  })

  output$table <- renderTable({
    req(input$species)
    selected() |>
      summarise(
        n = n(),
        mean_mass = mean(body_mass_g, na.rm = TRUE)
      )
  })
}

shinyApp(ui, server)
TipDoing nothing until the user has chosen

Before a user interacts, inputs hold their initial values — in the app above, input$species starts as the empty string "", because that is the placeholder entry. Calling req(...) at the start of a reactive block tells the block to produce nothing until its arguments are non-empty. Used inside a render* function this leaves the corresponding output blank, which is the simplest way to implement a requirement like “do not display anything until the user has made a selection”. For a customised message instead of a blank space, look up validate() and need().

7.6 Common Use Cases

Shiny is widely used in a variety of contexts where interactive data exploration, visualization, or reporting is valuable. Common use cases include:

  • Interactive dashboards: Creating dynamic dashboards for monitoring key metrics, business intelligence, or research results.
  • Data exploration tools: Allowing users to filter, subset, and visualize data interactively without writing code.
  • Statistical analysis apps: Providing interfaces for running statistical models, simulations, or hypothesis tests with user-specified parameters.
  • Educational tools: Building interactive tutorials, quizzes, or demonstrations for teaching statistics, data science, or other quantitative subjects.
  • Reporting and decision support: Enabling stakeholders to explore scenarios, adjust assumptions, and view results in real time.
  • Prototyping and sharing analyses: Rapidly developing and sharing prototypes of data products or analyses with collaborators or clients.

Shiny is especially useful when you want to empower non-programmers to interact with data or models, or when you need to communicate results in a more engaging and flexible way than static reports allow. To see what is possible, browse the Shiny gallery: two well-known examples are Movie Explorer, which combines a scatterplot with filters and selectors over a films dataset, and Radiant, an entire statistics package built as a shiny app.

7.7 Limitations

While Shiny is a powerful tool, it has several limitations:

  • Performance: Shiny apps can become slow with large datasets or complex computations, as all processing is handled on the server side and R is single-threaded by default.
  • Scalability: Each user session runs a separate R process, which can limit scalability for many simultaneous users unless additional infrastructure (e.g., Shiny Server Pro, load balancing) is used.
  • Security: Shiny apps can expose your R environment to users, so care must be taken to sanitize inputs and avoid code injection vulnerabilities.
  • Deployment: Deploying Shiny apps for public access often requires additional setup, such as using shinyapps.io or configuring a Shiny Server, which usually cost money.
  • Limited UI Customization: While Shiny provides many UI components, highly customized or modern web interfaces may require additional HTML, CSS, or JavaScript knowledge.
  • Dependency on R: Shiny apps require an R environment to run, which may not be suitable for all deployment scenarios.

Understanding these limitations helps in deciding when Shiny is the right tool and when alternative solutions (such as static reports, other dashboard frameworks, or web technologies) may be more appropriate.
