5  Data Wrangling II - Joins, Strings and Dates

Objectives

  • Describe “messier” data types structures that might be encountered in the real world.
  • Be able to join tables together using join functions.
  • Be able to deal with date and string types.

5.1 Joins: Connecting Multiple Tables

A join combines rows from two or more tables based on a related column between them. There are various types of joins depending on what kinds of data you want to join; we’ll go through each of them. To illustrate we will use the (synthetic) student data from student_data.csv and student_grades.csv.

library(tidyverse)
student_data = read_csv("data/student_data.csv")
student_grades = read_csv("data/student_grades.csv")
head(student_data)
# A tibble: 6 × 4
     ID `Given Name` `Family Name` `Date of Birth`
  <dbl> <chr>        <chr>                   <dbl>
1     1 Adaora       Nkomo                   37205
2     2 Hiroshi      Tanaka                  37845
3     3 Aaliyah      Williams                37505
4     4 Dimitri      Volkov                  37717
5     5 Amara        Baptiste                37387
6     6 Rajesh       Krishnamurthy           38218
head(student_grades)
# A tibble: 6 × 3
  `Student ID` Course   Grade
         <dbl> <chr>    <dbl>
1            1 MATH6195    68
2            2 MATH6195    67
3            3 MATH6195    68
4            4 MATH6195    74
5            5 MATH6195    52
6            6 MATH6195    85

We have two tables, and they are linked by a common ID column (called Student ID in student_grades). Names and dates of birth are available in student_data but the student grades are in student_grades. Each student takes multiple courses, so the relationship between the student and grade tables is one-to-many.

TipWhy Store Data Like This?

Storing in multiple tables is good practice for multiple reasons:

  1. Data size: If we stored it in a single flat table, the student name would be repeated for every course they take. This can make the data files significantly larger!
  2. Consistency and Integrity: If a student changes their name, it only needs to be updated in one place.
  3. Flexibilty: Adding new attributes is much easier. For example, if we wanted to start recording student reference requests, we could add a new student_references table, with a one-to-many relationship with student_data but no link at all to student_grades.
  4. Clarity: It’s easier to think about the data structure if it is logically separated like this (e.g. “each student takes multiple courses”).

5.1.1 Cleaning Column Names

Before we go further, notice that these column names are awkward to work with: some contain spaces (Student ID, Date of Birth) and the capitalisation is inconsistent. Every time we refer to such a name we have to wrap it in backticks — for example student_grades$`Student ID` — which is easy to forget and clutters our code.

The clean_names function from the janitor package fixes this in a single step, converting every column name to a consistent snake_case style with no spaces or capitals. We will clean both tables now and keep the tidied versions, so that the rest of this chapter can refer to columns without backticks:

library(janitor)
student_data = clean_names(student_data)
student_grades = clean_names(student_grades)
names(student_data)
[1] "id"            "given_name"    "family_name"   "date_of_birth"
names(student_grades)
[1] "student_id" "course"     "grade"

So Given Name becomes given_name, Date of Birth becomes date_of_birth, and the two columns that link the tables are now id (in student_data) and student_id (in student_grades). Cleaning names up front like this is often the very first thing worth doing when you load a messy dataset, and it is a good habit to get into.

5.1.2 Inner Join

An inner join takes two tables and joins them together into a single table on based on the matching column, returning only rows that exist in both tables.

result = inner_join(student_data, student_grades, by=c("id" = "student_id"))
head(result)
# A tibble: 6 × 6
     id given_name family_name date_of_birth course   grade
  <dbl> <chr>      <chr>               <dbl> <chr>    <dbl>
1     1 Adaora     Nkomo               37205 MATH6195    68
2     1 Adaora     Nkomo               37205 MATH2010    59
3     1 Adaora     Nkomo               37205 MATH2011    58
4     2 Hiroshi    Tanaka              37845 MATH6195    67
5     2 Hiroshi    Tanaka              37845 MATH2010    72
6     2 Hiroshi    Tanaka              37845 MATH2011    72

Notice how the result contains the columns from both tables. The column we joined on appears only once (as id, its name in the left table), rather than being duplicated as both id and student_id.

Tipby = c(...) and join_by()

The by = c("id" = "student_id") syntax says “match the id column in the left table to the student_id column in the right table”. Recent versions of dplyr provide a newer, more flexible alternative called join_by(), which you will increasingly see in documentation and online:

inner_join(student_data, student_grades, join_by(id == student_id))

Both forms do the same thing here. join_by() uses == (rather than a named string), and can also express more advanced matches such as joining on inequalities. We will use the by = c(...) form in these notes, but the two are interchangeable for our purposes.

Let’s look at the rows.

nrow(result)
[1] 53
nrow(student_grades)
[1] 59

See result has fewer rows than student_grades. This must mean there are some student IDs in the student_grades table that are not in the student_data table. Let’s check:

setdiff(student_grades$student_id, student_data$id)
[1] 21 22

There are two missing students from student_data. Because this is an inner join these were excluded from the final table. Let’s now check if there are any students in student_data that are not present in the result.

setdiff(student_data$id, result$id)
[1] 7

It seems the student with ID 7 is missing:

result |>
    filter(id == 7)
# A tibble: 0 × 6
# ℹ 6 variables: id <dbl>, given_name <chr>, family_name <chr>,
#   date_of_birth <dbl>, course <chr>, grade <dbl>

To check why this might be, we can look for that student in the student_grades table:

student_grades |>
    filter(student_id == 7)
# A tibble: 0 × 3
# ℹ 3 variables: student_id <dbl>, course <chr>, grade <dbl>

So the student is missing because they have no grade records, so the inner join excludes them from the final table. Hopefully they have applied for special considerations!

5.1.3 Left / Right Join

Left and right join keep all the records in the left table or the right table, respectively, in the join statement. Let’s see what the result looks like with a left join instead:

result = left_join(student_data, student_grades, by=c("id" = "student_id"))
result |> filter(id == 7)
# A tibble: 1 × 6
     id given_name family_name date_of_birth course grade
  <dbl> <chr>      <chr>               <dbl> <chr>  <dbl>
1     7 Lin        Yifan               38146 <NA>      NA

Now the student who has no student_grades records is still present in the final table. However, because there are no grade records, the table is filled with <NA> under course and grade. Right join is essentially the same, but keeps records in the right table.

5.1.4 Outer Join

Outer join keeps records in both tables. In dplyr this is called a full_join; this matches SQL’s FULL OUTER JOIN (see ?sec-sql), which is often shortened to just “full join”.

result = full_join(student_data, student_grades, by=c("id" = "student_id"))
result |> filter(id == 7)
# A tibble: 1 × 6
     id given_name family_name date_of_birth course grade
  <dbl> <chr>      <chr>               <dbl> <chr>  <dbl>
1     7 Lin        Yifan               38146 <NA>      NA

We see that the result contains the student with missing grades, but it will also contain the two students who were missing in the student_data table:

result |> filter(id %in% c(21,22))
# A tibble: 6 × 6
     id given_name family_name date_of_birth course   grade
  <dbl> <chr>      <chr>               <dbl> <chr>    <dbl>
1    21 <NA>       <NA>                   NA MATH6195    70
2    22 <NA>       <NA>                   NA MATH6195    89
3    21 <NA>       <NA>                   NA MATH2010    71
4    22 <NA>       <NA>                   NA MATH2010    56
5    21 <NA>       <NA>                   NA MATH2011    62
6    22 <NA>       <NA>                   NA MATH2011    84

Now the given_name, family_name and date_of_birth fields are all <NA>.

5.1.5 Other Types of Join

There are some other types of join which are much less common to encounter. Here are some examples:

  • semi_join(x, y, by="id"): keeps rows in x that have a match in y but does not add columns from y.
  • anti_join(x, y, by="id"): keeps rows in x that do not have a match in y, but again does not add columns from y.
  • cross_join(x,y): gives the cartesian product of x and y, that is, the tibbles are not matched on any common column, but rather all possible combinations of rows in x and y appear.
WarningTwo common surprises when joining

Duplicated column names. If both tables contain a (non-key) column with the same name — say both have a notes column — the join cannot keep them both under one name. By default dplyr disambiguates them by adding the suffixes .x (from the left table) and .y (from the right), giving notes.x and notes.y. You can control these with the suffix argument.

Many-to-many joins. Our student example is one-to-many: each student has many grades, but each grade belongs to one student. If instead both tables have several matching rows for a key (a many-to-many relationship), the join produces a row for every combination of matches, which can multiply the number of rows dramatically. Recent versions of dplyr will warn you when this happens, as it is very often a sign of a mistake in the join.

5.2 Strings

We often need to deal with purely textual data in data science. While it would be nice for all the data we receive to be highly structured, we frequently get “free text” input from users, where the input may need to be cleaned or otherwise processed before it can be used. In tidyverse this is the role of the stringr library, which provides a large family of functions (all prefixed with str_) that are designed to work nicely with the tibble format.

A key feature of every stringr function is that it is vectorised: it works on a single string or on a whole vector (or column) of strings, which is exactly what we need when cleaning a column of a data frame.

str_length("Hello World")
[1] 11
str_length(c("Alice", "Bob", "Dave"))
[1] 5 3 4

To illustrate the main operations we will use a small vector of deliberately messy names, of the kind you might get from a free-text form:

messy_names <- c("  Alice  ", "BOB", "cara-mae", "  dave ")

5.2.1 Measuring and Extracting

str_length returns the number of characters, and str_sub extracts a substring between two positions. Positions count from 1, and negative positions count from the end of the string:

str_sub("MATH6195", 1, 4)   # first four characters
[1] "MATH"
str_sub("MATH6195", -4, -1) # last four characters
[1] "6195"

5.2.2 Standardising Case

Inconsistent capitalisation is one of the most common problems in free text. str_to_lower, str_to_upper and str_to_title standardise it:

str_to_lower(messy_names)
[1] "  alice  " "bob"       "cara-mae"  "  dave "  
str_to_title(messy_names)
[1] "  Alice  " "Bob"       "Cara-Mae"  "  Dave "

5.2.3 Trimming Whitespace

Stray spaces are another frequent nuisance, and they are easy to miss because they are invisible. str_trim removes leading and trailing whitespace, while str_squish also collapses repeated internal spaces down to a single space:

str_trim(messy_names)
[1] "Alice"    "BOB"      "cara-mae" "dave"    
str_squish("  too    many   spaces ")
[1] "too many spaces"

5.2.4 Detecting and Matching

str_detect tests whether each string contains a pattern, returning a logical vector — which makes it ideal for use inside filter(). str_starts and str_ends are convenient special cases for the beginning and end of a string:

str_detect(messy_names, "a")   # which names contain a lower-case "a"?
[1] FALSE FALSE  TRUE  TRUE
str_starts(messy_names, "B")
[1] FALSE  TRUE FALSE FALSE

Note that matching is case-sensitive: "Alice" does not match "a" because it contains an upper-case "A". A common pattern is therefore to standardise case with str_to_lower before matching.

5.2.5 Replacing and Removing

str_replace replaces the first match of a pattern, str_replace_all replaces every match, and str_remove / str_remove_all delete matches entirely:

str_replace("cara-mae", "-", " ")      # first match only
[1] "cara mae"
str_replace_all("a-b-c-d", "-", "_")   # every match
[1] "a_b_c_d"
str_remove("MATH6195", "MATH")
[1] "6195"

5.2.6 Splitting and Combining

str_split breaks a string into pieces on a separator. It returns a list, because each input string might split into a different number of pieces:

str_split("MATH6195,MATH6196,MATH6197", ",")
[[1]]
[1] "MATH6195" "MATH6196" "MATH6197"

Going the other way, str_c joins strings together — either element-by-element (like paste0), or into a single string using the collapse argument:

str_c("MATH", 6195)                  # element-wise; numbers are coerced to text
[1] "MATH6195"
str_c(messy_names, collapse = ", ")  # collapse a vector into one string
[1] "  Alice  , BOB, cara-mae,   dave "

5.2.7 Putting It Together

Because these functions are vectorised, they slot directly into a dplyr pipeline. Here we clean a whole column of raw names in a single mutate, squishing out stray whitespace and standardising the case:

tibble(raw = messy_names) |>
    mutate(clean = str_to_title(str_squish(raw)))
# A tibble: 4 × 2
  raw         clean   
  <chr>       <chr>   
1 "  Alice  " Alice   
2 "BOB"       Bob     
3 "cara-mae"  Cara-Mae
4 "  dave "   Dave
TipRegular Expressions

The pattern argument to functions like str_detect, str_replace and str_split is not just plain text: it is interpreted as a regular expression. A regular expression is a “mini language” that allows you to describe flexible patterns to search for, such as “a run of digits” or “an @ surrounded by letters” — which is how you would detect phone numbers or email addresses entered into a free-text box. The simple patterns we used above ("a", "-", ",") happen to be literal text, so they behave as you would expect; but be aware that some characters (such as ., * and ?) have special meanings. We won’t cover regular expressions in detail in this course, but they are well worth knowing about. A good resource for learning is regex101.

5.3 Dates

When we imported the student data above, there was a column — now called date_of_birth after cleaning — that did not appear to contain dates:

student_data$date_of_birth
 [1] 37205 37845 37505 37717 37387 38218 38146 37596 38167 37590 37472 37803
[13] 37283 37852 37900 37865 38162 37870 37282 37481
typeof(student_data$date_of_birth[1])
[1] "double"

The numbers above are Excel format dates. They are the number of days that have elapsed since Excel’s “day zero”, which is December 30, 1899. In theory we could process these dates using this knowledge, but it is much more convenient to convert the number to a proper date type in R. This (and more) functionality is provided by lubridate, a package in tidyverse.

5.3.1 Loading and Converting Dates

Loading dates is surprisingly complex because there is no standard format. For example, here are a variety of perfectly valid ways to represent the date “11th August 2025”:

dates = c(
    '2025-08-11',
    '11/08/2025',
    '08/11/2025',
    '11 August, 2025',
    '11-Aug-2025'
)

The list above is non-exhaustive, so some domain knowledge will always be required to load dates. R may try to infer a date format, but it might be wrong. It is always safer to specify the date format, or at least, to carefully check that dates have been loaded correctly before doing any data analysis.

lubridate provides several helper functions to convert from some standard formats, that are fairly robust to different sub conventions like delimeters or padding.

today1 = ymd("2025-August-11")
today2 = dmy("11/08/25")
today3 = mdy("8.11.2025")
c(today1, today2, today3)
[1] "2025-08-11" "2025-08-11" "2025-08-11"

R has correctly inferred the date in all three cases. We can also use the as.Date function to customise parsing further, by providing a format string to describe how the date string is expected to be formatted. For more information on formatting see the as.Date documentation.

Note that while the dates are printed as strings, they do in fact have a date type:

class(today1)
[1] "Date"

For the Excel date example, if we read Excel files with readxl there won’t be a problem. But, sometimes Excel dates make their way into other file formats, and we can use the janitor package to load them.

student_data$date_of_birth = excel_numeric_to_date(student_data$date_of_birth)
student_data$date_of_birth
 [1] "2001-11-10" "2003-08-12" "2002-09-06" "2003-04-06" "2002-05-11"
 [6] "2004-08-19" "2004-06-08" "2002-12-06" "2004-06-29" "2002-11-30"
[11] "2002-08-04" "2003-07-01" "2002-01-27" "2003-08-19" "2003-10-06"
[16] "2003-09-01" "2004-06-24" "2003-09-06" "2002-01-26" "2002-08-13"

5.3.2 Date Processing

Once dates are in the proper format, there exist various functions to process them. For example, we can extract the year, month or day:

c(year(today()), month(today()), day(today()))
[1] 2026    9   21

For example, if we want to compute a student’s age we can use lubridate’s interval function followed by time_length

student_data$age = interval(student_data$date_of_birth, today()) |>
    time_length("years")
student_data$age
 [1] 24.86301 23.10959 24.04110 23.46027 24.36438 22.09041 22.28767 23.79178
 [9] 22.23014 23.80822 24.13151 23.22466 24.64932 23.09041 22.95890 23.05479
[17] 22.24384 23.04110 24.65205 24.10685
student_data$age |> floor()
 [1] 24 23 24 23 24 22 22 23 22 23 24 23 24 23 22 23 22 23 24 24

Or, we could use as.period to get a precise calendar difference:

interval(student_data$date_of_birth, today()) |>
    as.period(unit="years")
 [1] "24y 10m 11d 0H 0M 0S" "23y 1m 9d 0H 0M 0S"   "24y 0m 15d 0H 0M 0S" 
 [4] "23y 5m 15d 0H 0M 0S"  "24y 4m 10d 0H 0M 0S"  "22y 1m 2d 0H 0M 0S"  
 [7] "22y 3m 13d 0H 0M 0S"  "23y 9m 15d 0H 0M 0S"  "22y 2m 23d 0H 0M 0S" 
[10] "23y 9m 22d 0H 0M 0S"  "24y 1m 17d 0H 0M 0S"  "23y 2m 20d 0H 0M 0S" 
[13] "24y 7m 25d 0H 0M 0S"  "23y 1m 2d 0H 0M 0S"   "22y 11m 15d 0H 0M 0S"
[16] "23y 0m 20d 0H 0M 0S"  "22y 2m 28d 0H 0M 0S"  "23y 0m 15d 0H 0M 0S" 
[19] "24y 7m 26d 0H 0M 0S"  "24y 1m 8d 0H 0M 0S"

We could also just subtract the dates, but this gives a difference in terms of days which would be difficult to convert to years (due to leap years).

today() - student_data$date_of_birth
Time differences in days
 [1] 9081 8441 8781 8569 8899 8068 8140 8690 8119 8696 8814 8483 9003 8434 8386
[16] 8421 8124 8416 9004 8805

5.3.3 Times and Time Zones

Times can be handled similarly to dates. There are routines for loading times that are similar to the date-specific routines described above:

time1 = ymd_hms("2025-08-11 11:33:01")
time1
[1] "2025-08-11 11:33:01 UTC"
time2 = now()
time2
[1] "2026-09-21 11:08:36 BST"

We can then extract hours, minutes and seconds:

c(hour(time1), minute(time1), second(time1))
[1] 11 33  1

One extra consideration with times is the time zone. For example, we can see that the time zone of time1 and time2 differ, above:

c(tz(time1), tz(time2))
[1] "UTC" ""

Note that tz(time2) returns an empty string, which is standard in R for the current time zone. If we want to be explicit we can force now to be in a particular time zone, e.g.

time3 = now("Asia/Tokyo")
tz(time3)
[1] "Asia/Tokyo"

We can also change the time zone on times using the with_tz function:

with_tz(time1, "Asia/Tokyo")
[1] "2025-08-11 20:33:01 JST"
time1
[1] "2025-08-11 11:33:01 UTC"

Notice that this adjusts the time from the previous time zone (UTC) to match the new time zone (JST). If we want to add a time zone without changing the time, we use the force_tz function:

force_tz(time1, "Asia/Tokyo")
[1] "2025-08-11 11:33:01 JST"

Now the time is the same as time1, but the time zone has been modified.

5.3.4 Formatting Dates and Times

By default invoking today1 in R uses the specific format 2025-08-11. We may wish to use another format, for which we can invoke the format function. This takes a date and a format string (as per as.Date, above), and outputs a string in that format. For example:

format(today1, "%Y-%m-%d")
[1] "2025-08-11"
format(today1, "%d %b %y")
[1] "11 Aug 25"
format(time1, "%d %b %y %H:%M")
[1] "11 Aug 25 11:33"
